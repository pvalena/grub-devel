# AI Review: MR !241 - IBM client architecture (CAS) reboot support

1 commit: on IEEE 1275 firmware, every executed script is saved in the `boot-last-label` NVRAM property, and when the
firmware reports a CAS reboot, `grub_normal_execute()` re-executes that script and runs `boot` right after the config
is read.

**Commits:**
1. **eefdc8f34** - IBM client architecture (CAS) reboot support

## Issues Found

4 issues, all in the single commit.

### Issue 1: `script` is reallocated through a by-value copy, so the caller keeps a freed pointer

**Location:** `grub-core/kern/ieee1275/openfw.c`, `grub_ieee1275_cas_reboot()`, lines 671-672;
`grub-core/normal/main.c`, `grub_normal_execute()`, lines 293-300

`main.c:294` does `script = grub_malloc (1024)` with no NULL check and passes the pointer by value. If
`boot-last-label` is longer than 1024 bytes, `cas_reboot` does `script = grub_realloc (script, actual + 1)`, which
only changes its own copy. A block from `grub_malloc (1024)` has exactly 1024 payload bytes, so `grub_realloc` cannot
grow it in place (`mm.c:720-741`): it allocates a new block, copies, and **frees the caller's block**. The label is
then read into the new block, but `grub_normal_execute()` still holds the freed pointer. It runs
`grub_script_execute_sourcecode (script)` on stale, uninitialised memory (whose first statement stores that text into
`boot-last-label`), and `grub_free (script)` (`main.c:300`) then hits an already-freed block (`grub_fatal`
"double free" / "alloc magic is broken", `mm.c:150-154`) or, if the block was reused, someone else's. The new block
leaks. The `grub_malloc` result is also never checked: on failure `script == NULL` is passed to `getprop` as the
destination buffer.

**Draft fix** -- let `cas_reboot` allocate exactly `actual + 1` and hand the buffer back (also covers Issue 2):

```diff
--- a/grub-core/kern/ieee1275/openfw.c
+++ b/grub-core/kern/ieee1275/openfw.c
@@ grub_ieee1275_cas_reboot
-grub_ieee1275_cas_reboot (char *script)
+grub_ieee1275_cas_reboot (char **script)
@@
-      if (! grub_ieee1275_get_property_length (options, "boot-last-label", &actual))
+      if (! grub_ieee1275_get_property_length (options, "boot-last-label", &actual)
+          && actual > 0)
         {
-          if (actual > 1024)
-            script = grub_realloc (script, actual + 1);
-          grub_ieee1275_get_property (options, "boot-last-label", script, actual,
-                                      &actual);
-          return 0;
+          grub_ssize_t len = actual;
+          char *buf = grub_malloc (len + 1);
+
+          if (buf == NULL)
+            return -1;
+          if (grub_ieee1275_get_property (options, "boot-last-label", buf, len, &actual))
+            {
+              grub_free (buf);
+              return -1;
+            }
+          buf[len] = '\0';
+          *script = buf;
+          return 0;
         }
--- a/grub-core/normal/main.c
+++ b/grub-core/normal/main.c
@@ grub_normal_execute
-      char *script;
-      script = grub_malloc (1024);
-      if (! grub_ieee1275_cas_reboot (script))
+      char *script = NULL;
+      if (! grub_ieee1275_cas_reboot (&script))
```

(the prototype in `include/grub/ieee1275/ieee1275.h` changes to `char **script` as well)

### Issue 2: The saved label is executed without a terminating NUL, and an empty label is accepted

**Location:** `grub-core/kern/ieee1275/openfw.c`, `grub_ieee1275_cas_reboot()`, lines 669-674, and
`grub_ieee1275_set_boot_last_label()`, lines 692-693

`set_boot_last_label()` stores exactly `grub_strlen (text)` bytes (no NUL). `cas_reboot` reads back `actual` bytes
into `script`, ignores the return value, and never writes `script[actual] = '\0'`. The consumer,
`grub_script_execute_sourcecode()`, treats `source` as a C string (`grub_strchr`, `grub_strdup`, `execute.c:891-896`),
so unless the firmware returns a NUL that GRUB never stored, parsing continues past the label into the rest of the
(uninitialised) heap block; an `actual` of exactly 1024 leaves no room even in the original buffer. The same file's
`grub_ieee1275_get_boot_dev()` (`openfw.c:605-632`) shows the intended pattern: reject `size <= 0`, over-allocate, set
`bootpath[bootpath_size] = '\0'`. Also, the clear path writes an empty string (`openfw.c:679`) but the check at
`openfw.c:669` only tests that the property exists, not that it is non-empty. If the firmware keeps a zero-length
property, a CAS reboot with an empty label takes `actual == 0`, returns 0, and the caller executes the uninitialised
buffer (I did not check whether firmware keeps zero-length properties). See the draft fix in Issue 1.

### Issue 3: `eval` overwrites the saved label with its own string

**Location:** `grub-core/script/execute.c`, `grub_script_execute_sourcecode()`, line 909;
`grub-core/commands/eval.c:54`

The label is saved in `grub_script_execute_sourcecode()`, the common executor, which `eval` also calls. An entry such
as `menuentry "A" { eval "set x=1"; linux /vmlinuz; initrd /initrd }` first saves its own body
(`menu.c:302` -> `grub_script_execute_new_scope()` -> `execute.c:952`), then `eval` replaces it with `set x=1`. After
the CAS reboot GRUB reads back `set x=1`, executes it successfully, runs `boot` with nothing loaded ("you need to load
the kernel first", `boot.c:197`) and falls through to the menu, so the boot is not resumed. Saving in
`grub_script_execute_new_scope()` instead (only two callers: the entry executor `menu.c:302` and the menu editor
`menu_entry.c:1216`) records the entry that was actually run.

**Draft fix** -- move the save to the entry-level wrapper:

```diff
--- a/grub-core/script/execute.c
+++ b/grub-core/script/execute.c
@@ grub_script_execute_sourcecode
   struct grub_script *parsed_script;
 
-#ifdef GRUB_MACHINE_IEEE1275
-  grub_ieee1275_set_boot_last_label (source);
-#endif
-
   while (source)
@@ grub_script_execute_new_scope
   new_scope.flags = 0;
 
+#ifdef GRUB_MACHINE_IEEE1275
+  grub_ieee1275_set_boot_last_label (source);
+#endif
+
   old_scope = scope;
```

### Issue 4: `%lu` is passed a `grub_size_t`, a `-Wformat` error on the 32-bit ports

**Location:** `grub-core/kern/ieee1275/openfw.c`, `grub_ieee1275_set_boot_last_label()`, line 689

`grub_dprintf("ieee1275", "set boot_last_label (size: %lu)\n", grub_strlen(text))` formats a `grub_size_t` with
`%lu`. On 32-bit ports (`i386-ieee1275`, 32-bit `powerpc-ieee1275`) that is `grub_uint32_t`, i.e. `unsigned int`
(`types.h:140`), and `PRIuGRUB_SIZE` is `"u"` there (`types.h:148`). `grub_real_dprintf` carries
`__attribute__ ((format (GNU_PRINTF, 5, 6)))` (`misc.h:614-618`), `-Wall` and, when the compiler accepts it,
`-Wformat=2` are in the target flags (`configure.ac:541-542, 640, 653-667`), and `-Werror` is on unless
`--disable-werror` is given (`configure.ac:2583-2589`). `openfw.c` is built for every IEEE 1275 port
(`Makefile.core.def:184`), and the only other `%lu` in the file (line 551) takes an `unsigned long`, so this is the
first mismatch. Expected result: a `-Wformat` error on those two ports with a default configure. This was not
confirmed by compiling. On 64-bit ports `grub_size_t` is `unsigned long`, so `%lu` matches there.

**Draft fix** -- use the size_t format macro:

```diff
--- a/grub-core/kern/ieee1275/openfw.c
+++ b/grub-core/kern/ieee1275/openfw.c
@@ grub_ieee1275_set_boot_last_label
-  grub_dprintf("ieee1275", "set boot_last_label (size: %lu)\n", grub_strlen(text));
+  grub_dprintf ("ieee1275", "set boot_last_label (size: %" PRIuGRUB_SIZE ")\n", grub_strlen (text));
```

## Additional findings

Not reported as issues (detail in the reasoning file): the NVRAM read/clear/write runs on every IEEE 1275 port, not only
POWER, and the `set_property` result is ignored. The replayed label runs without the entry-level `entry->restricted`
check (`menu.c:215-216`): whoever can write `/options` `boot-last-label` and set a CAS flag gets a script run at the
next start without the GRUB password (needs NVRAM write access; who can write `/options` is not checkable from the
tree; only the per-command `grub_verify_string()` applies).
