# AI Review: MR !216 - grub-mkconfig: avoid temp-file races

1 commit fixing a race condition in `util/grub-mkconfig.in` when
concurrent processes generate grub.cfg simultaneously.

**Commits:**
1. **c698db848** - grub-mkconfig: avoid temp-file races in concurrent runs

Commit messages accurately describe the changes.

## Issues Found

### Issue 1: `mv` replaces file metadata (permissions, ownership, ACLs)

**Location:** `util/grub-mkconfig.in`, install path for non-symlink
targets, lines ~335-337

The old code used `cat ${grub_cfg}.new > ${grub_cfg}` which
truncates and rewrites the existing file, preserving its inode and
therefore its permissions, ownership, and extended attributes. The
new non-symlink path uses `mv`, which is a `rename()` call that
replaces the directory entry entirely. The destination gets the temp
file's metadata: mode 0600 (from `umask 077`), owned by the
invoking user (root), with default ACLs/SELinux context.

If `grub.cfg` previously had non-default permissions (e.g., 0644
for monitoring tools that read it as non-root), those are silently
lost on every `grub-mkconfig` run. The symlink path correctly
preserves the old `cat >` behavior, but the non-symlink path does
not.

Not a straightforward fix. Several approaches exist with different
trade-offs:

- Save and restore permissions with `stat`/`chmod`: correct but
  relies on GNU coreutils `stat -c %a`, which is not POSIX.
- Use `cat >` followed by `rm`, as in the symlink path: preserves
  metadata but loses the atomicity that `mv` provides (the entire
  point of this MR for non-symlink targets).
- Use `install -m` with a saved mode: similar portability concerns
  as `stat`.

The author needs to decide whether atomicity or metadata
preservation takes priority for non-symlink targets. A reasonable
compromise would be `mv` followed by `chmod` to restore at least
the file mode, accepting that ownership and ACLs may still change.
