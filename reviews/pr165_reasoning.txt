== Issue 1: /0 prefix triggers undefined behavior (net.c) ==

Discovery:
Reading the new cidr validation in grub_cmd_addaddr at lines
~1177-1186. The check `cidr < 0` rejects negative values but
allows cidr=0. Traced what happens when mask=0 reaches
grub_net_add_ipv4_local.

Source trace:
grub_cmd_addaddr parses "/PREFIX" from args[2]:

  p = grub_strchr(args[2], '/');
  cidr = -1;
  if (p) {
    cidr = (int)grub_strtol(&p[1], &q, 10);
    if ((! q) || (q[0] != '\0') || (cidr > 31) || (cidr < 0))
      return grub_error(..., "invalid network prefix");
    p[0] = '\0';
  }

For input "10.0.0.1/0":
1. p points to "/"
2. grub_strtol("0", &q, 10) returns 0, q points to '\0'
3. Validation: (!q) false, (q[0]!='\0') false, (0>31) false,
   (0<0) false → passes
4. p[0] = '\0' strips the "/0"
5. grub_net_add_ipv4_local(inf, 0) is called

In grub_net_add_ipv4_local (line ~1144):

  route->target.ipv4.base =
    grub_cpu_to_be32(ip_cpu & (0xffffffff << (32 - mask)));

With mask=0: 0xffffffff << (32 - 0) = 0xffffffff << 32.

C99 section 6.5.7p3: "If the value of the right operand is
negative or is greater than or equal to the width of the
promoted left operand, the behavior is undefined."

0xffffffff is unsigned int (32-bit on all GRUB platforms).
Shifting by 32 is >= the width, so the behavior is undefined.

Before this patch, grub_net_add_ipv4_local was called with
mask=-1 (which triggers auto-detection producing 8, 16, or 24,
or early return for class D/E). mask=0 was never reachable.

Cross-reference: on x86, the SHL instruction masks the shift
count to 5 bits (Intel SDM Vol. 2B), so << 32 becomes << 0,
giving 0xffffffff. On ARM, the barrel shifter returns 0 for
shift amounts >= 32. The route base address would be
architecture-dependent.

Consequence:
Typing "net_add_addr iface card 10.0.0.1/0" at the GRUB shell
triggers undefined behavior. On x86, the route base becomes
10.0.0.1/0 (matching all IPs — default route behavior). On ARM,
the route base becomes 0.0.0.0/0. In neither case is the result
likely what the user intended.

Fix assessment:
Changing `cidr < 0` to `cidr < 1` rejects /0 and eliminates the
UB path. /0 is not meaningful for local routing (it means "all
addresses are local"), so rejecting it is reasonable. The fix
does not affect any valid prefix value (1-31).

== Issue 1: Docs put [/PREFIX] on the interface argument (grub.texi) ==

Discovery:
Reading the docs commit 2f6a1cb5b against the code commit. The synopsis
line became
  @deffn Command net_add_addr @var{interface[/PREFIX]} @var{card} @var{address}
while the commit message says "optional /PREFIX appended to the ADDRESS
argument".

Source trace:
- net.c:1177 p = grub_strchr (args[2], '/'): the prefix is split off
  args[2], the third argument (ADDRESS). args[0] is used only at net.c:
  1198, grub_net_add_addr (args[0], ...).
- grub_net_add_addr (net.c:280-295) grub_strdup()s the name and
  grub_net_add_addr_real (net.c:253-277) stores it unchanged;
  grub_net_network_level_interface_register (net.c:962-1000) does no
  validation of the name (it only builds net_<name>_mac / net_<name>_ip
  variables). So "efinet0/28" is an accepted interface name.
- The usage string registered at net.c:2181 is
  "SHORTNAME CARD ADDRESS[/PREFIX] [HWADDRESS]", and commit c931ec3cb's
  example is "net_add_addr efinet0 efinet0 10.0.0.140/28". Both put the
  prefix on ADDRESS.
- The adjacent node net_add_route documents the same optional prefix as
  @var{ip}[/@var{prefix}] (grub.texi, net_add_route node), so the
  intended style is clear.

Consequence:
A user who follows the rendered synopsis types
"net_add_addr efinet0/28 efinet0 10.0.0.140". No error is raised: an
interface named "efinet0/28" is created, grub_net_add_ipv4_local (inf,
-1) gives it the class-A default 10.0.0.0/8 route named
"efinet0/28:local", and the requested /28 is silently not applied.
Documentation-only defect; the code is right.

Fix assessment:
Moving the optional part to the address, "@var{address}[/@var{prefix}]",
matches the code, the usage string and net_add_route. The prose line
"if @var{/PREFIX} is not specified" should use the same @var{prefix}
spelling. Adding "(1 to 31)" states the range the code enforces
(net.c:1182). Texinfo-only change, no build impact.

== Issue 2: (int) cast defeats the cidr > 31 range check (net.c) ==

Discovery:
Reading the validation after the /0 fix, the question was whether
"cidr > 31" and "cidr < 1" really bound the user's number. cidr is an
int (net.c:1165) but is assigned from (int)grub_strtol(...) (net.c:
1181), and grub_strtol returns long.

Source trace:
- grub_strtol (misc.h ~338-372) calls grub_strtoull, then only checks
  "magnitude > GRUB_LONG_MAX" for overflow; otherwise returns
  (long) magnitude. A value in 32..GRUB_LONG_MAX is returned intact.
- GRUB_LONG_MAX is 9223372036854775807L when GRUB_CPU_SIZEOF_LONG == 8
  (types.h:165-166), so long is 64-bit there. The net module is built
  with "common = net/net.c" (Makefile.core.def:2522), i.e. on every
  platform including the 64-bit EFI ones. On 32-bit targets long is
  already int-sized and an out-of-range value is caught by the overflow
  check (returns GRUB_LONG_MAX = 0x7fffffff > 31), so they are fine.
- (int) of a long outside int range is implementation-defined; GCC and
  Clang reduce it modulo 2^32. 4294967324 = 2^32 + 28 -> 28. Negatives
  wrap the same way: -4294967268 -> 28. Values that overflow long
  (> GRUB_LONG_MAX) are returned as GRUB_LONG_MAX = 0x7fff...ffff, whose
  low 32 bits are 0xffffffff -> -1 -> rejected. Values 2^31 .. 2^32-1
  wrap to a negative int and are still rejected by cidr < 1; only values
  >= 2^32+1 whose residue mod 2^32 is 1..31 are wrongly accepted (e.g.
  4294967324 -> 28). The negative side is the same idea: values below
  -2^31 whose residue mod 2^32 is 1..31 are accepted (-4294967268 -> 28).
- q ends at the terminating NUL for such a string (the digits are all
  consumed), so the q[0] != '\0' test does not catch it either.

Consequence:
"net_add_addr n0 card 10.0.0.140/4294967324" succeeds and installs
local route 10.0.0.128/28 instead of printing "invalid network prefix".
Only nonsense input is affected, and the truncated value is always in
1..31 when it passes, so the later shift in grub_net_add_ipv4_local()
stays defined: validation hole, not a memory-safety problem. Low impact,
but the cast sits directly in the one check this patch adds to bound the
input.

Fix assessment:
Declaring cidr as long and dropping the cast makes the 1..31 test apply
to the real value. The later call grub_net_add_ipv4_local (inf, cidr)
converts to the int parameter only after validation (or with the initial
-1), so the conversion is value-preserving. grub_strtol's overflow
return (GRUB_LONG_MAX) is still > 31 and rejected. No other use of cidr.
