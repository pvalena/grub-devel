Final design in one paragraph
-----------------------------
configfile (and extract_entries_configfile) call grub_cls_deferred() instead of grub_cls().  For each active
output: if the terminal implements the new ->prepare callback and has not yet been "activated"
(GRUB_TERM_OUTPUT_ACTIVE clear), only GRUB_TERM_CLEAR_PENDING is set; otherwise the old behavior (newline for
dumb/debug, else cls) runs.  Only the EFI console implements ->prepare (console.c:481).  Its
grub_prepare_for_text_output() is the single place where the firmware text console is switched to "available"
(console.c:149-157); the patch hooks the pending clear and the ACTIVE bit there, so the first putchar/getwh/
gotoxy/cls on an untouched console performs the clear, and a configfile that never prints never clears.

Commit 1 - dbd414894 "configfile: Defer screen clear until visible output"
--------------------------------------------------------------------------
What it does: configfile.c installs configfile_xputs() as grub_xputs for the outermost configfile
(configfile_depth 0 -> 1), keeps clear_pending/clear_generation per nesting level (saved in locals, restored
after grub_normal_execute), and cls is issued on the first non-empty xputs unless grub_cls_generation moved
(bumped in grub_cls() and in the inline grub_term_cls(), exported from kern/term.c via EXPORT_VAR).
Traced:
 - Install/restore are balanced: no early return between "if (new_env) {...}" and the matching restore
   block; grub_normal_execute() returns void; old_clear_* locals are only read under the same new_env test
   that writes them.
 - saved_xputs is grub_xputs_normal at install time: configfile references grub_normal_execute and grub_cls
   (module normal), and GRUB_MOD_INIT(normal) takes grub_dl_ref(mod) ("Normal mode shouldn't be unloaded"),
   so GRUB_MOD_FINI(normal) (which resets grub_xputs) cannot run while the hook is installed.
 - Nested case: inner configfile saves outer pending/generation, sets its own, restores on exit; depth counter
   keeps the hook installed until the outermost returns.  A visible menu inside the configfile calls
   grub_term_cls() (menu_text.c), which bumps the generation, so a later first xputs does not clear again.
 - Limitation the next commit addresses (and the commit message of commit 2 states): output that bypasses
   grub_xputs (help uses print_ucs4 directly) is not seen by the hook.
No defect found in this commit as a standalone change.  It is wholly removed by commit 2 (hook, depth
counter, grub_cls_generation definition/export/increments all gone; no reference left at pr323:
`rtb grep cls_generation --ref pr323` returns nothing).

EFI state machine (term/efi/console.c)
--------------------------------------
Variables: global text_mode (UNDEFINED at boot; set only at line 156 and 465), per-term flags ACTIVE/PENDING.
 - prepare (141-170): returns BAD_DEVICE if grub_efi_is_finished; returns early (line 149-150) whenever
   text_mode != UNDEFINED.  So ACTIVE/PENDING handling runs exactly once per UNDEFINED -> AVAILABLE
   transition, and ACTIVE is set on the same path that sets text_mode, so ACTIVE == (text_mode AVAILABLE) for
   the single EFI console term.
 - fini (457-466): clears ACTIVE|PENDING first, then, if text_mode == AVAILABLE, disables the cursor and
   resets text_mode to UNDEFINED.  Flags and text_mode therefore return to the same pair of states together.
   fini is invoked from commands/terminal.c (--remove and the "not in list" removal pass), never when the console
   is merely re-selected, so a re-selected active console stays ACTIVE.
 - cls (440-452): clears PENDING before calling prepare, so a prepare that happens inside cls cannot also do
   the deferred clear; the explicit clear then runs once.  Trace: pending set, `clear` command ->
   grub_cls -> grub_console_cls: PENDING off, prepare sets ACTIVE (no clear), one clear_screen.  One clear total.
 - Pending path: untouched console, configfile -> PENDING.  First output: print_ucs4_real calls
   term->getxy (console.c:419 returns {0,0} while text_mode != AVAILABLE).  The EFI console is
   VISUAL_GLYPHS, so it takes the bidi path, which evaluates get_maxwidth (-> grub_term_width -> getwh ->
   prepare) and get_startwidth (getxy) as arguments of grub_bidi_logical_to_visual.  C leaves that argument
   order unspecified, but getxy gives {0,0} both before the clear (text_mode UNDEFINED) and after it (cursor
   homed), so either order yields the same start column.  prepare then does ACTIVE, clear_screen with a black
   background, attribute restored; putchar follows.  Same for gotoxy/putchar/cls as the first caller.  The
   block is a copy of grub_console_cls's clear sequence (o->mode->attribute, set_attributes, clear_screen,
   restore); same types and macros, so it should compile on every EFI target the file already builds for.
 - Hidden-menu autoboot (the motivating case): run_menu with timeout_style hidden loops on
   grub_getkey_noblock/grub_key_is_interrupt (EFI getkeystatus: no output), on timeout returns default entry
   with notify_boot = (style != HIDDEN) = 0; show_menu calls grub_menu_execute_with_fallback (the grub_cls() at
   menu.c show_menu is only in the non-auto_boot branch).  No term callback that calls prepare runs, PENDING stays
   set and the splash survives until something prints.
 - Visible menu on an untouched EFI console: the pending clear is consumed by the width query, not by the
   explicit cls.  grub_menu_init_page (menu_text.c) calls grub_term_width() first (menu_text.c:342), which
   prepares the console and performs the deferred clear; it then calls grub_normal_init_page (menu_text.c:410),
   whose first statement is grub_term_cls (main.c:218) (or grub_term_cls directly at menu_text.c:412 when the
   version line is dropped), which clears again.  Two clears in total, the same count as before the MR
   (immediate configfile clear plus the menu's own clear), so the extra clear is harmless.  When the console is
   already active, grub_cls_deferred clears immediately as before and the menu's cls is the second clear.
 - terminal_output switch (console -> gfxterm): console is removed, fini clears PENDING; gfxterm has no
   ->prepare so grub_cls_deferred clears it immediately as before.
 - Non-EFI terminals (serial/terminfo, pc console, vga_text, ieee1275, uboot, xen, arc, gfxterm): prepare is
   NULL, so grub_cls_deferred == immediate clear (dumb/debug -> newline, else grub_term_cls), same as the old
   grub_cls() for terminals that define ->cls.  The two empty-output early returns are the only change there.

sleep --verbose
---------------
sleep.c:85 prepares before grub_term_save_pos.  On the EFI console the call does perform the pending clear
(prepare, console.c:141-170, clear at 159-167); what it does not change is the saved cursor position: while
PENDING is set text_mode is UNDEFINED, getxy reports {0,0}, and the clear leaves the cursor at {0,0}, so
save_pos yields {0,0} either way (without the call, the first do_print's restore_pos -> gotoxy would trigger
the same clear).  So the call has no visible effect there.  It matters for terminals whose getxy reports the
real cursor before prepare
(the test's fake terminals, and any future ->prepare implementer).  normal/menu.c run_menu (countdown style:
grub_term_save_pos then print_countdown) is the same pattern and works on EFI for the same reason; it is not
touched by the patch and does not need to be.  Non-verbose sleep skips prepare, so PENDING is preserved
(test section 6).

Empty-output early returns (caller audit)
-----------------------------------------
grub_xnputs: callers are grub_xputs_normal (grub_strlen), cbmemc.c replay (sizes may be 0; nothing to print),
and the test.  Before the patch an empty string still ran print_ucs4_real, whose first act is term->getxy and
whose argument evaluation reaches getwh -> prepare, i.e. an empty `echo -n ""` could activate the EFI console
(and consume the pending clear).  After: no terminal call at all.  grub_xputs_dumb already did nothing for "".
grub_print_ucs4: callers are print_more (non-empty "--MORE--"), grub_normal_init_page (main.c:239, non-empty
version banner, and that function starts with an explicit grub_term_cls), help.c:81 (prefix of the command
text), menu_entry.c:1113 (completion window).  All pass margin_left == margin_right == 0, so the only thing
skipped for an empty range is the getxy/getwh query; no margin spaces are lost.  Void return, no caller
depends on a side effect.

Command availability (settled from source): help/sleep/echo/true are separate modules that the test does not
insmod, so they resolve through dynamic-command stubs.  Chain: grub_main calls grub_load_normal_mode
(kern/main.c:233, called at :368), which loads normal and runs the `normal` command; with no argument that goes
through grub_cmd_normal -> grub_enter_normal_mode (config) -> grub_normal_execute (config, 0, 0), i.e. the root,

Observations recorded, not reported as issues
---------------------------------------------
1. Precedence of pending over debug/dumb: grub_cls_deferred() tests `prepare && !ACTIVE` before the DUMB/debug
   newline rule.  On an untouched EFI console with the `debug` variable set, the old grub_cls() printed a newline
   (screen kept); now the screen is cleared at the first output.  Nothing GRUB drew can be lost (the console was
   untouched), only firmware/previous-stage text, and EFI console is not DUMB.  No concrete failure, so not an
   issue.
2. ACTIVE means "prepared", not "visibly printed": any getwh/gotoxy/putchar/cls on the EFI console consumes a
   pending clear, including geometry queries in dry-run line counting.  All such callers found are in drawing
   contexts (menu, help, message printing); the new empty-output returns remove the one query-only path I found.
3. The ACTIVE/PENDING bits are written by terminal drivers, while the comment above the flag block in term.h still
   says the flags are "used by higher-level functions but not terminals themselves".  Comment-only mismatch.
4. The clear sequence is duplicated between grub_prepare_for_text_output and grub_console_cls (could share a
   helper).  Style only.
5. Series shape: commit 1's implementation is fully reverted by commit 2 and commit 4 repairs whitespace commit 2
   removed; squashing 1+2 and 3+4 would make bisect/review simpler.  Every intermediate state read as
   self-consistent (commit 1 references only symbols it defines/exports).
6. Pre-existing, outside this MR (present on origin/master, not touched by the diff): the out-of-memory fallback
   loop in grub_xnputs(), `for (; msg_len--; str++, msg_len++)`, re-increments msg_len each iteration and never
   terminates for msg_len != 0.  Needs a failed grub_calloc to reach.  The new msg_len == 0 early return does not
   change it.
