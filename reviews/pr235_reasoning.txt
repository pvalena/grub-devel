== Issue 1: zero-fill past the end of the input is unreachable (fuzz/grub_fuzzing_platform.c) ==

Discovery:
Reading fuzz_disk_read_cb() (lines 141-166) the two branches that zero-fill, `byte_offset >= data_len` (line
149) and `avail < bytes` (line 159), looked like they depend on GRUB ever asking the device for bytes beyond
the image. The claim is made in three places, each worded differently: the commit 5afa7bac1 message
("zero-fills reads past the end of the input, which lets a parser be driven from an arbitrarily short
input"); the code comment at lines 137-139 ("Any region past the end of the image is zero-filled, which is
safe: filesystem probers will see an invalid superblock and return GRUB_ERR_BAD_FS"); and docs/grub-dev.texi
:736-738, added by commit e0ebb339d (fuzz_disk_set_image: "Reads past the end of the input are zero-filled,
so a parser can be driven from a short input"). fuzz_disk_open() at line 120 sets
`disk->total_sectors = fuzz_disk_logical_size () >> GRUB_DISK_SECTOR_BITS`, and fuzz_disk_logical_size()
(lines 94-98) returns fuzz_image_size unchanged. That made me check whether GRUB's disk layer lets a request
beyond total_sectors reach the callback at all.

Source trace:
1. grub_disk_open() (grub-core/kern/disk.c:298-399) calls each registered device's disk_open until one
   succeeds and does not alter disk->total_sectors afterwards; the only post-open check that matters here is
   the log_sector_size range (disk.c:350-357). fuzz_disk_dev is registered last by fuzz_grub_init(), but
   grub_disk_dev_register() puts it at the head of grub_disk_dev_list (disk.c:260-264), and fuzz_disk_open()
   returns UNKNOWN_DEVICE for any other name, so "fuzzdev" is served by the fuzz callbacks with the
   total_sectors above.
2. Every filesystem read goes through grub_disk_read(): grub_ext2_mount() reads the superblock with
   `grub_disk_read (disk, 1 * 2, 0, sizeof (struct grub_ext2_sblock), ...)` (ext2.c:690), and the group
   descriptor, inode and block reads are grub_disk_read() calls too (ext2.c:421, 472, 606, 671).
3. grub_disk_read() (disk.c:527-) begins with `grub_disk_adjust_range (disk, &sector, &offset, size)` and
   returns the error if it fails (disk.c:533-540).
4. grub_disk_adjust_range() (grub-core/kern/disk_common.c:6-51): line 33
   `total_sectors = disk->total_sectors << (disk->log_sector_size - GRUB_DISK_SECTOR_BITS)`; lines 41-42 clamp
   to GRUB_DISK_MAX_SECTORS (1 << 51, include/grub/disk.h:171); lines 44-48
   `if (total_sectors <= *sector || ((*offset + size + 511) >> 9) > total_sectors - *sector)
      return grub_error (GRUB_ERR_OUT_OF_RANGE, "attempt to read or write outside of disk `%s'", ...)`.
   So any request whose last byte is at or past total_sectors * 512 never reaches the device.
5. The device callback (dev->disk_read) is called from exactly three places in disk.c:
   - disk.c:458-461 in grub_disk_read_small_real(), only under
     `disk->total_sectors == GRUB_DISK_SIZE_UNKNOWN || sector + GRUB_DISK_CACHE_SIZE < total_sectors`
     (lines 453-455; GRUB_DISK_CACHE_SIZE is 64 sectors, disk.h:190), i.e. the whole 64-sector unit is
     inside the disk;
   - disk.c:494 in the fallback of the same function, reading `num` sectors computed from the (already
     range-checked) size and offset, starting at the requested sector (lines 481-488);
   - disk.c:606 in the agglomerate loop of grub_disk_read(), sized from the range-checked `size`.
   In all three the sector range handed to the callback is inside [0, total_sectors). With
   total_sectors = size >> 9, that is [0, floor(size / 512) * 512) bytes, a subset of the input, so
   byte_offset < data_len and avail >= bytes hold for every call and both zero-fill branches are dead.
6. Worked example, 3000-byte input with a 1 KiB-block image: total_sectors = 5. The superblock (sectors 2-3)
   and a group descriptor at block 2 (sector 4) are readable. grub_ext2_read_inode() for inode 2 then reads
   the inode table, typically at block 5 or later (sector >= 10): adjust_range sees `total_sectors (5) <=
   sector` and returns OUT_OF_RANGE; the callback is never called. grub_ext2_mount() reaches `fail:` and
   rewrites OUT_OF_RANGE to GRUB_ERR_BAD_FS "not an ext2 filesystem" (ext2.c, `fail:` label after
   grub_ext2_read_inode (data, 2, ...)). With the documented behaviour the read would have returned a
   zero-filled inode and mount would have continued.
7. Tail bytes: size 4100 gives total_sectors 8, so bytes 4096-4099 are in no readable sector. For size < 512,
   total_sectors is 0 and no byte is readable.

Consequence:
Nothing is corrupted or leaked; the cost is fuzzing effectiveness and misleading documentation. Inputs shorter
than a full image, which libFuzzer produces constantly by truncation, stop at an out-of-range error rather than
exercising the driver against zero-filled metadata; up to 511 trailing bytes per input are inert; the harness
comment and the manual describe behaviour the code does not have, and the manual is what authors of the next
fuzz targets are told to rely on.

Fix assessment:
Not a straightforward single fix because the intent is ambiguous (docs say zero-fill, code makes it dead).
Option (a), a capacity larger than the input: trace with a fixed 1 GiB capacity
(GRUB_DISK_KiB_TO_SECTORS (1024 * 1024) = 1 << 21 sectors, disk.h:200): adjust_range passes for any sector
below 2^21; grub_disk_read_small_real() takes the full-unit branch (453-455) and the callback zero-fills past
the data; `(grub_size_t) sector << 9` is at most 2^30, which fits a 32-bit grub_size_t. Using
GRUB_DISK_SIZE_UNKNOWN instead would also work on 64-bit hosts (clamped to 1 << 51 by disk_common.c:41-42)
but on a 32-bit host `sector << 9` would truncate and alias high sectors onto low image offsets, so a bounded
capacity is the safer sketch. Either way the ext2 driver can then follow block pointers into zero-filled space,
which changes timing and what is reachable; that is a decision for the author. Option (b), deleting the claim
and the dead branches, needs no behaviour decision.
Side effect of option (a) on the build: fuzz_disk_logical_size() is `static` (fuzz/grub_fuzzing_platform.c:
93-98) and fuzz_disk_open() line 120 is its only caller (searched the whole pr235 tree). Replacing that line
leaves an unused static function; -Wunused-function is in WARN_FLAGS (configure.ac:541) and -Werror is added
to HOST_CFLAGS unless --disable-werror is given (configure.ac:2586-2588), and fuzz_cflags starts from
$(AM_CFLAGS) = $(HOST_CFLAGS) (Makefile.am:20), so the platform file would stop compiling. The sketch in the
review therefore also deletes the function (repurposing it would work equally well).

AI-assistance scrutiny:
The harness is locally careful (every path through LLVMFuzzerTestOneInput closes the disk and calls
fuzz_grub_reset; label and UUID are freed; the callback's arithmetic is correct in isolation). The miss is a
global-contract one: the comment asserts GRUB will hand the device out-of-range reads, without tracing
grub_disk_read(), where the core rejects them first.


== Issue 2: fuzz-get-corpus leaves its temporary clone behind on failure (Makefile.fuzz.am) ==

Discovery:
Reading the new recipe (Makefile.fuzz.am:117-127, commit eb9881694): it starts with `set -e;`, creates a
temporary directory with `mktemp -d`, and removes it with a plain `rm -rf $$tmpdir` as the last command.

Source trace:
- The recipe is one shell command (backslash continuations), run by `/bin/sh -c`; `$(AM_V_GEN)` expands to an
  `@echo ...;` prefix or to nothing (AM_INIT_AUTOMAKE([1.11 ...]), configure.ac:83), neither of which changes
  that.
- Under `set -e` the first failing simple command ends the shell. The commands after `mktemp -d` that can
  fail: `git clone ... -b $(FUZZ_CORPUS_BRANCH) $(FUZZ_CORPUS_REPO) $$tmpdir` (unreachable remote, unknown
  branch), `git -C $$tmpdir sparse-checkout set corpus`, `git -C $$tmpdir checkout` (with
  `--filter=blob:none` this is where the blobs are fetched, so it needs the network again),
  `mkdir -p fuzz/corpus`, `cp -r $$tmpdir/corpus/. fuzz/corpus/` (which also fails if the checkout contains
  no `corpus/` directory).
- No trap and no other cleanup exists in the recipe, and no other rule removes the directory, so on any of
  these failures `$$tmpdir` stays in `$TMPDIR` (/tmp by default).
- Convention elsewhere in the tree: recipes that write a partial or temporary file remove it on the failure
  branch, e.g. `|| (rm -f $@.new; exit 1)` (conf/Makefile.common:160, 166) and `|| (rm -f $@; exit 1)`
  (Makefile.am:58, 62), so cleaning up on failure is the established pattern; this recipe does not follow it.

Consequence:
What the recipe text alone establishes: after a failed `mkdir`/`cp` the whole fetched corpus (commit message:
"a large and continually growing collection of binary inputs") stays in `$TMPDIR`, as does the partial clone
after a failed `checkout`, because nothing removes the directory. For a failed `git clone` (the commit
message names an offline machine and a work-in-progress branch as intended uses) the directory is expected to
remain, at least empty, because git keeps a pre-existing empty destination directory; that is git's behaviour,
which is not readable in this tree, so it is stated as expected rather than established. Low impact per
occurrence, but it accumulates on retries and is worst when the failure is "no space left".

Fix assessment:
`trap 'rm -rf "$$tmpdir"' EXIT` placed right after `mktemp -d` runs on normal exit and on `set -e` exit in
POSIX sh (dash and bash both run the EXIT trap in both cases). `$$tmpdir` inside single quotes is passed to the
shell as `$tmpdir` and expanded when the trap fires, after the variable is set. If `mktemp -d` itself fails,
`set -e` ends the shell before the trap is installed and there is nothing to remove. The trailing `rm -rf` is
then redundant and removed in the draft, which also keeps `cp` as the last command so its status becomes the
recipe's status.
