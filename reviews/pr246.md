# AI Review: MR !246 - Make "exit" take a return code

1 commit: `exit [CODE]` passes a status to `grub_exit (int)`, which gains an `int` parameter on every platform (EFI
maps nonzero to `EFI_LOAD_ERROR`, U-Boot and the host utilities pass it on, the other firmware ports ignore it).

**Commits:**
1. **a93553df3** - Make "exit" take a return code.

## Issues Found

### Issue 1: A non-numeric `exit` argument exits with status 0 (success)

**Location:** `grub-core/commands/minicmd.c`, `grub_mini_cmd_exit()`, lines 204-215

The code treats `n == ~0UL` as "could not parse" and keeps the default `retval = -1`. But `grub_strtoul()` returns
`~0UL` only on overflow. For input with no digits it returns **0** and sets `GRUB_ERR_BAD_NUMBER`
(`grub-core/kern/misc.c:650-658`), and nothing here reads `grub_errno`. So `exit foo`, `exit -1` (GRUB's parser has
no sign handling, `-` is not a digit) and `exit ""` all reach `grub_exit (0)`, which is `EFI_SUCCESS` on EFI and
`grub_uboot_return (0)` on U-Boot. Plain `exit` is the failing status, so a typo or an empty argument turns a
failure into a success, with no error message.

**Draft fix** -- report the bad number instead of exiting:

```diff
--- a/grub-core/commands/minicmd.c
+++ b/grub-core/commands/minicmd.c
@@ -210,8 +210,9 @@ grub_mini_cmd_exit (struct grub_command *cmd __attribute__ ((unused)),
   if (argc == 1)
     {
       n = grub_strtoul (argv[0], 0, 10);
-      if (n != ~0UL)
-	retval = n;
+      if (grub_errno != GRUB_ERR_NONE)
+	return grub_errno;
+      retval = n;
     }
 
 #ifdef GRUB_MACHINE_EFI
```

### Issue 2: Plain `exit` no longer returns the same status on EFI and U-Boot, contrary to the commit message

**Location:** `grub-core/commands/minicmd.c:204` (`int retval = -1`), `grub-core/kern/efi/efi.c:153-163`,
`grub-core/kern/uboot/init.c:42-45`

The message says "By default we return the same exit status we did before this patch". `exit` with no argument
passes -1. On EFI only `retval == 0` maps to `GRUB_EFI_SUCCESS`, so -1 becomes `GRUB_EFI_LOAD_ERROR`, where the old
`grub_exit (void)` always passed `GRUB_EFI_SUCCESS`. On U-Boot -1 becomes `grub_uboot_return (1)`, where it used to
be `grub_uboot_return (0)`. `grub_abort ()` (now `grub_exit (1)`) changes the same way on both. Only
`grub_util_error` in the host utilities (`exit (1)` before and after) keeps its old status; in grub-emu the `exit`
command goes to `emu/main.c:grub_exit`, which calls `grub_reboot ()` and ignores the code. Separately, `exit a b`
used to exit and now returns `GRUB_ERR_BAD_ARGUMENT`, so GRUB keeps running. Whatever the intent, message and code
disagree, and every EFI user of the plain `exit` command now hands a different status back to whatever started GRUB.

Not a straightforward fix, the author has to decide which side is intended. To keep the old behaviour, the "no code
given" value must map to the pre-patch per-platform status (EFI success, U-Boot 0) while the explicit
`grub_exit (-1)` in U-Boot `grub_machine_init` (`init.c:81`) keeps meaning failure. If reporting failure by default
is intended, the commit message (and the `exit` description in the docs) should say so.

## Additional findings

Every `grub_exit` definition and caller in the tree is updated (`rtb grep grub_exit`; `i386/pc` keeps its assembly
`grub_exit`, which never reads arguments). The clang-only `abort()` stub added in `grub-core/kern/misc.c` is not
mentioned in the commit message and is not on `origin/master`; I found no failing path for it.
The Issue 1 fix does not reject trailing garbage, `0x` prefixes or values above `INT_MAX`; hardening, see reasoning.
