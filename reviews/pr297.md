# AI Review: MR !297 - grub-mkconfig module/device dedup + EFI BootNext consolidation

3 commits. The first two reduce redundant `insmod`/device-access lines in generated grub.cfg
(motivated by trimming TPM PCR 8 event-log bloat): a new tracking mechanism records modules
loaded unconditionally at the top level of grub.cfg so later sections can skip re-emitting them,
and `00_header.in` uses it to stop re-preparing the same device for font/theme/background. The
third is an independent cleanup that wraps all discovered EFI BootNext menu entries in a single
`if [ "$grub_platform" = "efi" ]` block instead of repeating the check per entry. All three
commits carry `Assisted-by: Claude:Opus-5.5 Gemini:gemini-3.8-flash`.

## Issues Found

### Issue 1: Module state file created without the umask hardening used for grub.cfg itself

**Location:** `util/grub-mkconfig.in`, lines ~304-318

`util/grub-mkconfig.in` already protects the generated config from other local users twice:
creating `${grub_cfg}.new` is wrapped in `umask 077`/restore, and the final copy onto
`${grub_cfg}` is wrapped the same way. This commit adds a third file in the same directory (the
module-tracking state file used for cross-script dedup) but creates it under whatever umask the
caller already had, not under `umask 077`:

```sh
if [ -n "${GRUB_MODULE_STATE_FILE}" ]; then
    export GRUB_MODULE_STATE_FILE
    > "${GRUB_MODULE_STATE_FILE}"
    trap 'test -n "${GRUB_MODULE_STATE_FILE}" && rm -f "${GRUB_MODULE_STATE_FILE}"' EXIT
```

By this point the `umask 077` window used for `${grub_cfg}.new` has already closed and been
restored. `GRUB_MODULE_STATE_FILE` is `"${grub_cfg}.modules"` whenever grub-mkconfig is invoked
with `-o FILE` — the normal, common invocation, not an edge case — so the shell redirection `>`
creates it at the ambient `0666 & ~umask` (e.g. `0644` under a typical `022` umask), i.e.
world-readable, unlike `grub.cfg`/`grub.cfg.new`'s deliberately-enforced `0600`. (The `mktemp`
fallback path, used only when no `-o` is given, is unaffected: GNU `mktemp` creates its file at
mode `0600` regardless of umask.)

While it exists (from creation until it's removed right after the grub.d loop, or via the EXIT
trap on early termination), any local user who can reach the file can read the list of modules
grub-mkconfig loaded unconditionally, including cryptodisk-related module names (e.g.
`gcry_rijndael`) on an encrypted-boot system. This is less sensitive than grub.cfg's own contents
(which can carry a superuser password hash), so it's a hardening inconsistency rather than a
credential leak — but it's a concrete gap against a pattern this exact function already enforces
twice for sibling files, live on essentially every real-world invocation.

**Draft fix** — reuse the same umask idiom already used twice elsewhere in this file:

```diff
--- a/util/grub-mkconfig.in
+++ b/util/grub-mkconfig.in
@@ -315,4 +315,6 @@
   if [ -n "${GRUB_MODULE_STATE_FILE}" ]; then
     export GRUB_MODULE_STATE_FILE
-    > "${GRUB_MODULE_STATE_FILE}"
+    oldumask=$(umask); umask 077
+    > "${GRUB_MODULE_STATE_FILE}"
+    umask $oldumask
     trap 'test -n "${GRUB_MODULE_STATE_FILE}" && rm -f "${GRUB_MODULE_STATE_FILE}"' EXIT
```

## Additional findings

Traced the cross-commit interaction in depth: the `00_header.in` "last one prepared" shortcut
(commit 2) never skips a module that genuinely needs re-emitting (checked all font/theme/
background combinations), and unmodified callers in other `util/grub.d/*.in` scripts safely
benefit from the shared state file without being touched, because `/etc/grub.d/*` always runs in
lexical (00_, 10_, 20_, ...) order and a GRUB `insmod` persists for the rest of the boot session.
`GRUB_DISABLE_MODULE_DEDUPLICATION=true` fully reverts the cross-section tracking as documented;
it does not gate the separate within-call dedup (the fix for the literal "insmod gcry_rijndael
twice" bug), which is narrower than the commit message's "restore the previous behavior" read
literally, but causes no incorrect output and matches the accurate `docs/grub.texi` wording.
Commit 3 (`31_efi_bootnext.in`)'s subshell-capture refactor was checked for scope-leak and
`set -e` exposure from the new `$(...)` wrapping — none found; the while-loop was already running
in a subshell pre-patch (pipe semantics), so behavior is unchanged there.
