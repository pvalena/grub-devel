# AI Review: MR !271 - disk/ieee1275/obdisk: Do not use "%.*s" in canonicalise_disk()

1 commit fixing `canonicalise_disk()` on 4-address-cell IEEE1275 controllers: `grub_snprintf()`
has no `"%.*s"` precision conversion, so the previous format string silently produced a
literal `"*s"` in the disk name, and the extra `(int) node_prefix_len` argument that no format
specifier consumed shifted every following `grub_snprintf()` call built this way onto the wrong
argument. Every disk behind such a controller ended up with the same broken name; only the
boot disk (named from the boot path) still worked.

## Additional findings

The fix truncates `canon` in place (`*unit_address = '\0';`) instead of using precision, then
prints with a plain `"%s"`. This is safe: `canon` originates from
`grub_ieee1275_canonicalise_devname()` (`kern/ieee1275/openfw.c`), which always returns a fresh
`grub_malloc()`'d buffer private to this call chain, not a cached/shared/const buffer (unlike
e.g. `grub_env_get()` storage) -- so mutating it here is not the const-storage-mutation bug
pattern. `unit_address` points strictly inside `canon`'s allocation (derived from
`grub_strrchr`/`grub_strchr` on `canon` itself), so the write cannot go out of bounds, and
`canonicalise_4cell_ua()` is called on the *untruncated* `unit_address` before the truncation,
so the real unit-address lookup is unaffected by the later in-place edit. Confirmed the claimed
GRUB printf limitation by reading `parse_printf_arg_fmt()` in `kern/misc.c`: `.` is consumed but
the following digit-loop does not treat `*` as a placeholder, so `%.*s` leaves `*` to be read as
the conversion character itself (an unrecognized specifier), which is exactly the argument
mis-alignment the commit describes.

Traced a leftover `real_unit_address` (from `canonicalise_4cell_ua()`) that is never freed on the
success path -- present unchanged in `origin/master` and not touched by this diff, so it is
outside this MR's scope.
