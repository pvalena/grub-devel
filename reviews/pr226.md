# AI Review: MR !226 - efi: set loaded image device path when missing

3 commits. Under Secure Boot the verifier loads images with a NULL device path (see
`kern/efi/sb.c`), leaving `loaded_image->file_path` and the `LOADED_IMAGE_DEVICE_PATH`
protocol NULL. This MR points both at the device path grub already built, saving/restoring
the originals so the image's loader frees its own allocation (Windows' bootmgfw hangs
walking a NULL device path).

**Commits:**
1. **74b6b14de** - efi/api: add GRUB_EFI_LOADED_IMAGE_DEVICE_PATH_PROTOCOL_GUID macro
2. **819b9a680** - efi/chainloader: set the loaded image device path when it is missing
3. **679169c40** - efi/linux: set the loaded image device path when it is missing

## Issues Found

Both issues are on the same error path: `handle_protocol()` for `LOADED_IMAGE_DEVICE_PATH`
returning failure (the protocol is entirely absent from the handle). It is a rare
"broken firmware / shim" path, but the cleanup on it is wrong in both files.

### Issue 1: `mempath` leaked on the protocol-missing error path (linux.c)

**Location:** `grub-core/loader/efi/linux.c`, `grub_arch_efi_linux_boot_image()`, lines ~259-273

`loaded_image->file_path` is set to `mempath` (line 259), then `handle_protocol()` is called
(line 261). `override_dp` is only set to `true` at line 273, *after* the error check. So the
`goto unload` at line 267 runs with `override_dp == false`, and the `unload:` cleanup
(lines 301-308, guarded by `if (override_dp)`) neither frees `mempath` nor restores
`loaded_image->file_path`. `mempath` is leaked, and `loaded_image->file_path` is left
pointing at it just before `grub_efi_unload_image()`.

**Draft fix** -- free `mempath` and clear the dangling pointer before unwinding:

```diff
       if (status != GRUB_EFI_SUCCESS)
         {
           grub_error (GRUB_ERR_BAD_FIRMWARE,
                 "missing protocol for loaded image device path");
+          loaded_image->file_path = NULL;
+          grub_free (mempath);
           goto unload;
         }
```

### Issue 2: `loaded_image->file_path` left dangling into a freed buffer before unload (chainloader.c)

**Location:** `grub-core/loader/efi/chainloader.c`, `grub_cmd_chainloader()`, lines ~455-470, 492-499

`loaded_image->file_path` is set to `fp` (line 455), which points inside the `file_path`
buffer. If `handle_protocol()` fails, the code does `goto fail` (line 464) while `file_path`
is still non-NULL (it is only nulled at line 470, after the reinstall). The `fail:` block
frees `file_path` (line 492) and then calls `grub_efi_unload_image()` (line 499) with
`loaded_image->file_path` still pointing into that just-freed buffer. If the firmware touches
`FilePath` during `UnloadImage`, it operates on freed memory.

**Draft fix** -- restore the original (NULL) `file_path` before unwinding:

```diff
       if (status != GRUB_EFI_SUCCESS)
         {
           grub_error (GRUB_ERR_BAD_FIRMWARE,
                 "missing protocol for loaded image device path");
+          loaded_image->file_path = NULL;
           goto fail;
         }
```

(`file_path` itself is already freed by the `fail:` path, so no leak there -- only the
dangling pointer needs clearing.)
