# AI Review: MR !226 - efi: set loaded image device path when missing (re-review)

3 commits. Under Secure Boot the verifier loads images with a NULL device path (see
`kern/efi/sb.c`), leaving `loaded_image->file_path` and the `LOADED_IMAGE_DEVICE_PATH`
protocol NULL. This MR points both at the device path grub already built, saving/restoring
the originals so the image's loader frees its own allocation (Windows' bootmgfw hangs walking
a NULL device path).

**Commits:**
1. **195ea7e98** - efi/linux: set the loaded image device path when it is missing
2. **9dc7e1578** - efi/chainloader: set the loaded image device path when it is missing
3. **74b6b14de** - efi/api: add GRUB_EFI_LOADED_IMAGE_DEVICE_PATH_PROTOCOL_GUID macro

## Re-review

Both issues from the previous round are fixed:

- **linux.c** (`mempath` leaked and `file_path` left dangling on the `handle_protocol()`
  failure path): the error branch now does `loaded_image->file_path = NULL; grub_free
  (mempath);` before `goto unload` — exactly the suggested fix.
- **chainloader.c** (`file_path` left dangling into a freed buffer before unload): the error
  branch now does `loaded_image->file_path = NULL;` before `goto fail`.

The GUID macro commit (`74b6b14de`) is unchanged from the prior round; its value matches the
EFI `EFI_LOADED_IMAGE_DEVICE_PATH_PROTOCOL` GUID (`bc62157e-3e33-4fec-9920-2d3b36d750df`).

chainloader.c was reworked beyond the fix — the restore now happens in
`grub_chainloader_unload()` via a heap `grub_chainloader_context` (`ctx`) carried through
`grub_loader_set_ex()` — so all three commits were re-reviewed in full. The override/restore
and ownership lifecycles are correct (details in the investigation file). Two non-failing
observations below.

## Issues Found

No issues found.

## Additional findings

- **`loaded_image_device_path_guid` should be `static` in chainloader.c** (`chainloader.c`,
  line ~49). It is defined non-`static`, unlike the identical variable in `linux.c` (line
  ~58) and every sibling GUID (`load_file2_guid`, `device_path_guid`). This needlessly
  exports the symbol from `chainloader.mod`. No in-tree collision exists today (linux.c's copy
  is `static`), so there is no current failure — but it is a real linkage/namespace defect: a
  future module defining the same name would register a shadowing global. Trivial fix:

  ```diff
  -grub_guid_t loaded_image_device_path_guid =
  +static grub_guid_t loaded_image_device_path_guid =
       GRUB_EFI_LOADED_IMAGE_DEVICE_PATH_PROTOCOL_GUID;
  ```

- **`saved_file_path` is dead in both files** (linux.c local `saved_file_path`; the
  `ctx->saved_file_path` field in chainloader.c). It is declared, initialized to NULL, and
  restored into `loaded_image->file_path`, but the original is never captured into it. This is
  correct *only* because the override is entered exactly when `loaded_image->file_path ==
  NULL`, so restoring NULL always matches. It is harmless but misleading (the comments say the
  originals are "kept"); either drop the field/variable or actually capture the original for
  clarity and robustness.
