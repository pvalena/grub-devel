== Issue 1: Memory leak in set_loader_default_entry() (bli.c) ==

Discovery:
Reading set_loader_default_entry() at line ~216. The function calls
get_efivar("LoaderEntryOneShot") and get_efivar("LoaderEntryDefault").
Traced get_efivar() (line ~177): it calls grub_efi_get_variable() which
returns a malloc'd buffer, then allocates a new buffer via grub_malloc()
for the UTF-16 to char* conversion, frees the original, and returns the
new allocation. So the return value is always heap-allocated.

grub_env_set() (grub-core/kern/env.c) copies the value string into its
own storage via grub_strdup(). It does not take ownership of the passed
pointer. Confirmed by reading grub_env_set implementation.

Neither oneshot_entry nor default_entry is freed after grub_env_set().
Both are leaked on every call. This function is called during BLI init,
so it leaks once per boot -- not catastrophic but a real leak in a
memory-constrained environment.

Fix verification: grub_free() after each grub_env_set() is correct.
The values are not referenced again after the set call.

== Issue 2: Incorrect error check in bump_counter() (bls_bumpcounter.c) ==

Discovery:
Reading bump_counter(), the code does:
  tries_left = grub_strtol(++tmp, (const char**) &tmp, 10);
  if (tmp != NULL)

This looked suspicious because grub_strtol's endptr semantics differ from
libc's strtol. Traced the call chain:

grub_strtol (grub-core/kern/misc.c:609) calls grub_strtoull (line 523).
grub_strtoull behavior for the end pointer:
- On success: *end points past the last parsed digit (line ~570)
- On parse failure (no digits): *end = str (the input, line ~540),
  grub_errno = GRUB_ERR_BAD_NUMBER
- On overflow: *end points past digits, grub_errno = GRUB_ERR_OUT_OF_RANGE

In NO case does grub_strtoull set *end to NULL. The pointer always points
somewhere into the input string. Therefore "if (tmp != NULL)" is always
true regardless of whether parsing succeeded or failed.

Consequence: If the boot counter string is malformed (e.g., "3-abc" or
"+nodigits"), grub_strtol returns 0 with grub_errno set, but the code
proceeds as if parsing succeeded. tries_left becomes 0, and the entry
gets renamed with tries_left=0 -- effectively consuming the boot attempt
on a malformed counter rather than reporting an error.

The same bug appears twice in bump_counter(): once for tries_left and
once for tries (the original count after the '-').

Fix verification: Checking grub_errno == GRUB_ERR_NONE is the standard
GRUB pattern for strtol error detection. See e.g. grub-core/kern/misc.c
grub_strtoul_real() callers throughout the codebase.

== Issue 3: Mutation of const environment value in get_entry_number() (menu.c) ==

Discovery:
Reading the new code in get_entry_number() for .conf suffix handling.
The variable val is declared const char * and assigned from grub_env_get().
grub_env_get() returns a pointer directly into the environment hash table's
internal storage -- it does NOT return a copy.

The new code does:
  ext = grub_strrchr(val, '.');
  if (ext && grub_strcmp(ext, ".conf") == 0)
    {
      *ext = '\0';              // NUL-terminate to strip .conf
      res = menuentry_eq(e->id, val);
      *ext = '.';               // restore
    }

This writes through a const char * into the environment's internal buffer.

Why this is a real bug, not just pedantic:
1. It is undefined behavior per the C standard. The compiler is entitled to
   assume const memory is not modified and may optimize based on that
   assumption (e.g., caching the value in a register across the write).
2. Even ignoring UB, the environment table is shared global state. If
   menuentry_eq() or anything it calls reads the "default" environment
   variable (which is the one being mutated here), it would see the
   truncated value. While menuentry_eq is simple string comparison today,
   this is fragile against future changes.
3. On some platforms, grub_env_get values could theoretically be in
   read-only memory (though currently they're heap-allocated).

Fix verification: grub_strndup(val, ext - val) creates a heap copy of
just the portion before ".conf", without modifying the original. The
NULL check on val_dup is needed because grub_strndup can fail (OOM).
The fix correctly preserves the existing "if (res)" check after the block.

== Issue 4: Mutation of environment variable blsdir via cast (bls_bumpcounter.c) ==

Discovery:
Reading grub_cmd_bls_bumpcounter() at lines ~157-161:
  blsdir = grub_env_get("blsdir");
  if (blsdir)
    use_efi_delimiter_for_path((char*) blsdir);

grub_env_get returns const char * to internal storage (same as Issue 3).
The cast to (char*) strips const. use_efi_delimiter_for_path() (defined
earlier in the file) iterates the string replacing '/' with '\\'.

This permanently modifies the blsdir value in the environment table.
Every subsequent grub_env_get("blsdir") will return the backslash version.
If any other code (e.g., blsuki's BLS entry loading) relies on blsdir
having forward slashes, it will break silently.

Unlike Issue 3 where the mutation is "restored", here the change is
permanent and intentional -- the author wanted backslashes for EFI path
operations. The correct approach is grub_strdup() before mutation, use
the copy, then grub_free().

No draft diff was included in the review because the fix requires
restructuring the surrounding code (the strdup'd copy needs to be used
in the subsequent path construction and freed at the end).

== Issue 5: handle not closed on error paths (bls_bumpcounter.c) ==

Discovery:
Reading the EFI file operations in grub_cmd_bls_bumpcounter(). The file
is opened via root->Open(&handle, ...) at line ~167. After this point,
handle is a valid EFI_FILE_PROTOCOL pointer that must be closed.

The function has a finish: label used by error gotos. At the finish label:
  finish:
    grub_free(file_info);
    return GRUB_ERR_BUG;

handle->Close(handle) is only called in the success path at line ~253,
just before the SetInfo call. The error paths that jump to finish:
- GetInfo failure (line ~175)
- bump_counter() failure
- filename too long for buffer
All leak the file handle.

In EFI, leaked file handles consume firmware memory from boot services
pool and may exhaust handle table entries. In practice this function is
called once per boot for the current BLS entry, so one leaked handle per
failed boot attempt -- not catastrophic but clearly a bug.

Fix: Add "if (handle) handle->Close(handle);" to the finish label before
grub_free(file_info). handle should be initialized to NULL at declaration
so the Close is only called when the file was actually opened.

== Issue 6: Incorrect include guard name (filesystem.h) ==

Discovery:
Reading include/grub/efi/filesystem.h, the include guard is:
  #ifndef GRUB_EFI_TPM_HEADER
  #define GRUB_EFI_TPM_HEADER 1

This is obviously a copy-paste from another header. To verify it causes
a real conflict (not just a cosmetic issue), checked whether the "real"
TPM header exists: include/grub/efi/tpm.h exists in-tree and uses:
  #ifndef GRUB_EFI_TPM_HEADER
  #define GRUB_EFI_TPM_HEADER 1

Confirmed: both files use the identical guard. If any translation unit
includes both (directly or transitively), whichever is included second
will be silently skipped entirely. This means either TPM definitions or
filesystem definitions would be missing, causing compile errors or worse,
missing declarations leading to implicit function calls.

Fix: Rename the guard in filesystem.h to GRUB_EFI_FILESYSTEM_HEADER.

== Issue 7: LoaderFeatures uses platform-dependent sizeof(long) (bli.c) ==

Discovery:
Reading set_loader_features() in bli.c:
  static long loader_features = ...;
  return grub_efi_set_variable("LoaderFeatures", &bli_vendor_guid,
                               &loader_features, sizeof(long));

The Boot Loader Interface specification (systemd BLI, adopted by other
bootloaders) defines LoaderFeatures as a 64-bit unsigned integer.

sizeof(long) is platform-dependent:
- x86_64-efi, aa64-efi: sizeof(long) = 8 (correct by accident)
- i386-efi, arm-efi: sizeof(long) = 4 (incorrect, writes only 4 bytes)

To verify that 32-bit EFI platforms are actually affected, checked
grub-core/Makefile.core.def for the bli module configuration:
  module = {
    name = bli;
    ...
    enable = efi;
  };

"enable = efi" means the module is built for ALL EFI platforms, including
i386-efi. On i386-efi, sizeof(long) == 4, so the EFI variable would be
set with only 4 bytes instead of 8. EFI variable consumers (e.g., systemd
reading LoaderFeatures) expect an 8-byte value and would either read
garbage in the upper 4 bytes or reject the variable as malformed.

Fix: Use grub_uint64_t for the variable type and sizeof(grub_uint64_t)
for the size parameter. This is consistent across all platforms.

== Issue 1: .conf default never matched, val_dup unused (menu.c get_entry_number) ==

Discovery:
The commit 2 delta between rounds is only the replacement of `*ext = '\0'; res = menuentry_eq (e->id, val);
*ext = '.';` with a strndup. Reading the resulting loop in full (menu.c lines 523-590) showed the strndup result is
only freed, never compared.

Source trace:
- menu.c 548: `if (menuentry_eq (e->title, val) || menuentry_eq (e->id, val)) { entry = i; break; }`.
- menu.c 554-568: for an entry with ->blsuki and val ending in ".conf": `val_dup = grub_strndup(val, ext - val);`
  then `res = menuentry_eq (e->id, val);` (line 562, argument is val) and `grub_free (val_dup);`.
- Reaching line 562 means the line-548 call menuentry_eq (e->id, val) just returned 0 for the same e and the same
  val. menuentry_eq (menu.c 498-519) is a pure function of its two strings, so line 562 returns 0 again; res is 0
  whenever val_dup != NULL. The block can never set `entry`.
- Where `default` gets a value: bli.c set_loader_default_entry() copies LoaderEntryOneShot/LoaderEntryDefault
  verbatim into the `default` variable (lines 218-239); a user can also `set default=foo.conf` by hand, the form
  commit 2 is written to accept (the BLI page itself describes identifiers with the .conf/.efi suffix removed, so
  the suffix form is not claimed to come from the BLI variables). blsuki_is_default_entry() only decides which entries
  blscfg creates (it compares against entry->filename); the boot-time selection is get_entry_number() via run_menu()
  (menu.c 627-641). The menuentry id of a BLS entry is the file name without ".conf" and without the boot counter
  (bls_create_entry, blsuki.c 1034-1082, commit 11), so "foo.conf" can only match "foo" through this block.
- res is declared `int entry, res;` (line 527) without initialiser; when grub_strndup() returns NULL line 560 is
  false, line 565 `if (res)` reads an indeterminate value. (OOM-only; the tail at lines 581-584 resets grub_errno
  and returns -1 if the allocation failure is the last error.)

Consequence:
A `default` value ending in ".conf", the case commit 2 is written to accept, silently falls through to the first
menu entry (get_entry_number returns -1, run_menu falls back to entry 0, menu.c 640-641). The
pre-rework code (in-place NUL write) did select the entry; the rework fixed the UB and broke the feature.

Fix assessment:
Comparing val_dup removes the dead comparison. `res = 0;` before the strndup makes the OOM case defined. The tail
of get_entry_number() already clears grub_errno from a failed strndup. Hoisting the strndup out of the loop would
avoid a malloc per entry, but is not required for correctness.

== Issue 2: leaks and a double free in grub_cmd_bls_bumpcounter() (bls_bumpcounter.c) ==

Discovery:
Re-reading the whole function after the prior-issue fixes, tracking each allocation/handle to every exit.

Source trace (line numbers of the pr124 file):
1. blsdir: line 157 grub_env_get(); line 160 `blsdir = grub_strdup (blsdir)` replaces the const env pointer with a
   heap copy (prior #4 fix). Exits afterwards: 180 (Open failed: frees old_path only), 272 and 276 (free
   new_path via 262, loader_boot_count_path via 267, file_info), `finish` 278-281 (Close, free file_info). The
   copy is used until line 261 and never freed. When `blsdir` is unset the pointer is the string literal, so a
   fix needs a separate `char *` owner variable (as in the draft).
2. new_path: allocated by grub_xasprintf in bump_counter() (lines 87/89), assigned line 226. Freed only at line 262
   on the success path. `goto finish` at 245 (len16 >= capacity) and 254 (SetInfo failure) skip it; finish does
   not free it.
3. root: `volume->OpenVolume (volume, &root)` line 149. `root` is referenced only at lines 99, 149 and 172 (the
   Open call); there is no root->Close anywhere in the file, so the handle returned by OpenVolume is dropped on
   every path. No other OpenVolume user exists in this tree (`rtb grep OpenVolume` finds only this file, so there
   is no in-tree sibling to compare with; the finding rests on the code alone).
4. Double free (added in the follow-up pass, confirmed by re-reading lines 184-217 and 278-281): line 200
   `grub_free(file_info);` runs inside `if (err == GRUB_EFI_BUFFER_TOO_SMALL)` and leaves `file_info` pointing at the
   freed block. Line 204 `if (grub_add (size, 4, &size_info))` (grub_add is __builtin_add_overflow, safemath.h 29;
   `size` and `size_info` are 64-bit) takes `goto finish` at line 207 when size + 4 wraps. `finish` (278-281) calls
   grub_free(file_info) on the same pointer. The other jump after the free, line 213, is reached with file_info
   assigned the NULL from the failed grub_malloc, so it is harmless. The overflow check and its `goto finish` were
   introduced by commit 10 (the delta of e9912d4a4 on bls_bumpcounter.c).
5. Lines 269-273 `if (err != GRUB_EFI_SUCCESS)` after Close/Flush: err was last assigned by SetInfo (line 248) and
   the SUCCESS check at 250 already left via `goto finish`, so this block is unreachable. Harmless, noted only.

Consequence:
Items 1 and 2 are small heap leaks (path length) in the pre-boot heap, per invocation (item 1 whenever `blsdir` is
set; item 2 on rename failure / over-long name). Item 3 leaves one firmware file handle per invocation open on the
ESP; the command runs once per boot attempt of each counted entry, so the impact is small but it is an unbalanced
Open, the same class as prior #5. Item 4 is a double free of the same address, which corrupts the grub_mm free
list; it needs GetInfo to answer BUFFER_TOO_SMALL with a required size within 4 of 2^64 (size + 4 wraps), i.e. a
broken firmware, so it is not expected in normal operation, but it is the path the new overflow check exists for.

Fix assessment:
The draft keeps the strdup copy in `blsdir_dup`, frees it and closes `root` at the three exits that can follow
OpenVolume success (Open failure, success epilogue, finish) and frees new_path at finish. new_path is NULL
until line 226, so freeing it at finish is safe for the earlier gotos (194, 207, 213, 223, 228). `file_info = NULL;`
after the first free makes the free in `finish` a no-op on the overflow path (grub_free(NULL) is safe), and `finish`
frees file_info exactly once, so the draft does not introduce a second double free. On the success path root is
closed after handle->Close().

== Issue 3: '+' that is not a boot counter leaves GRUB_ERR_BAD_NUMBER set (bls_bumpcounter.c) ==

Discovery:
After confirming prior #2 was fixed, traced the failure branches of the new `grub_errno == GRUB_ERR_NONE` tests to
see what state the caller observes. Compared with the two other counter parsers added in the same MR.

Source trace:
- bls_bumpcounter.c 124: any '+' means "counting in effect". The argument is menu.c 310-321 `blsuki->filename`:
  the file name with ".conf" already removed in place by bls_create_entry (blsuki.c 1035-1036), counter kept if
  present. bump_counter() 56-91: `*tmp = '\0'`, then grub_strtol (++tmp, ...). For a "+" at the end of the name,
  the string is "" and grub_strtoull (misc.c, `if (! found)`
  branch, 650-657) calls grub_error (GRUB_ERR_BAD_NUMBER, "unrecognized number") and sets *end = str.
- bump_counter() line 80-82: `else { return NULL; }`; grub_errno stays BAD_NUMBER. Caller lines 226-228
  `goto finish`, line 281 returns GRUB_ERR_BUG. menu.c line 321 calls grub_command_execute() and discards the
  result; nothing between there and the script run clears grub_errno.
- bls_create_entry (blsuki.c 1042-1076) and tries_left() (blsuki.c 254-288) both treat a non-numeric '+' as "no
  counter" (error_push/pop resp. `grub_errno = GRUB_ERR_NONE`), i.e. the MR itself expects names such as
  "fedora-6.8.0-rc1+" (kernel version with a trailing '+').
- Stale error reporting: grub_script_execute_cmdline() ends with grub_print_error() (execute.c 1117-1120); that
  prints "error: unrecognized number." and bumps grub_err_printed_errors. menu.c 329-330: `if (errs_before !=
  grub_err_printed_errors) grub_wait_after_message ();`, which waits for a key press for up to 10 s
  (menu.c 65-77). grub_script_parse() (script.c from line 343) does not consult grub_errno, so the script still runs.
- Second-number case: lines 69-79; `tries = grub_strtol (...)` failing sets BAD_NUMBER, the else branch only sets
  tries = -1; the function still returns a name, the rename proceeds and the command returns GRUB_ERR_NONE (line
  276) while grub_errno remains set; the same print/wait follows.

Consequence:
A BLS entry whose file name contains a '+' that is not followed by digits shows an error and a key-press wait on every
boot attempt (and no counter rename happens, which is the correct outcome). With the old `tmp != NULL` check the
same entry would have been renamed to "...+0-1.conf" (prior #2 consequence); now it is reported instead of being
treated as "no counter".

Fix assessment:
Clearing grub_errno where the parse failure is consumed makes the non-counter case silent (dprintf only, as for the
other "no counter" exits). The only caller of bump_counter() is line 226, and OOM from grub_xasprintf is a separate
NULL return that is not touched by the change.

== Issue 4: LoaderFeatures still written through `long` (bli.c set_loader_features) ==

Discovery:
Re-checking prior #7 against the rework (1ULL constants, sizeof(loader_features)).

Source trace:
- bli.c 51-63: `static long loader_features = <ORed 1ULL flags>;` and
  `grub_efi_set_variable("LoaderFeatures", &bli_vendor_guid, &loader_features, sizeof(loader_features))`. The size
  is now spelled sizeof(loader_features), which is sizeof(long): 8 on LP64, 4 on ILP32.
- Makefile.core.def 2851-2856: module bli, `enable = efi`. gentpl.py 55-56: GROUPS["efi"] = i386_efi, x86_64_efi,
  ia64_efi, arm_efi, arm64_efi, loongarch64_efi, riscv32_efi, riscv64_efi. i386_efi, arm_efi and riscv32_efi are
  32-bit platforms in this group.
- BLI spec (systemd.io, fetched): LoaderFeatures "contains a 64-bit unsigned integer with a number of flags bits".
  The highest flag set here is bit 18, so the value itself fits in 32 bits; the defect is the stored size, not
  truncated flag values.

Consequence:
On i386-efi, arm-efi and riscv32-efi the variable is written with a 4-byte payload instead of the 64-bit integer the
interface defines. I did not check how a given consumer reacts to a 4-byte value; the size mismatch against the
spec is the finding.

Fix assessment:
`static grub_uint64_t loader_features` makes sizeof() 8 on every platform and needs no other change (the macros are
already 1ULL; the call passes sizeof(loader_features)).

== Issue 5: advertised LoaderEntries ids differ from menu ids (UKI, non-numeric '+') (blsuki.c, menu.c) ==

Discovery:

Source trace:

  `boot_counting_idx = grub_strrchr (entry->filename, '+')`; if found, len = idx - filename (no check of what
  follows); else drop a trailing ".conf" (1531-1533, 1582-1584) or ".efi" (1534-1536, 1585-1587).
- entry->filename keeps its extension: blsuki.c 658 `entry->filename = grub_strndup (filename + path_len, ...)` after
  the loader accepted only names ending in ext (".conf" or ".efi", lines 609-630).
- UKI menu id: uki_create_entry() blsuki.c 1156 `char *id = entry->filename;` and 1219
  `grub_normal_add_menu_entry (1, argv, NULL, id, ...)`; nothing strips ".efi" (the same string is used as the file
  name in the chainloader command, line 1215, so it must keep the extension). Menu id of "fedora-6.8.0.efi" is
  therefore "fedora-6.8.0.efi"; advertised id is "fedora-6.8.0".
- BLS menu id: bls_create_entry() strips ".conf" in place (1035-1036) and removes a "+..." suffix only when the text
  between the last '+' and the next '-' (or the end) parses completely as a number (1042-1076:
  `n_end != n && *n_end == '\0'`). For "fedora-6.8.0-rc1+.conf": tries = "+", done = NULL, n = "", grub_strtol fails,
  default branch, no id_dup; menu id "fedora-6.8.0-rc1+"; advertised id "fedora-6.8.0-rc1" (cut at '+').
  For plain names and numeric counters ("fedora-6.8.0+3-1.conf" -> "fedora-6.8.0") both sides agree.
- Matching: get_entry_number() menu.c 546-568 compares `val` with e->title and e->id; its only suffix handling is
  ".conf" (line 557). For val = "fedora-6.8.0" and a UKI entry with id "fedora-6.8.0.efi", or val = "fedora-6.8.0-rc1"
  and id "fedora-6.8.0-rc1+", menuentry_eq() returns 0 for every entry, get_entry_number() returns -1 and run_menu()
  uses entry 0 (menu.c 640-641).
- The BLI page (fetched, model-summarised) says an identifier for BLS entries is "derived directly from the file
  name" with the ".conf" (Type #1) or ".efi" (Type #2) suffix removed, which is what LoaderEntries follows here.

Consequence:
An OS that reads LoaderEntries and writes one of those ids back to LoaderEntryDefault/LoaderEntryOneShot (or a user
who sets `default` to it) does not get that entry; the first menu entry boots instead, without a message. Affects
every UKI entry and every BLS entry whose name has a '+' not followed by a number.

Fix assessment:
No draft diff: the clean fix is a shared canonical-id helper used by bls_create_entry(), uki_create_entry() and both
loops of set_bli_loader_entries(). It changes the menu id of UKI entries from "foo.efi" to "foo", which may break
existing `default=foo.efi` configurations unless get_entry_number() keeps accepting the old form; that trade-off is
the author's decision. Patching only set_bli_loader_entries() to advertise "foo.efi" would contradict the id rule
quoted above.

== Issue 6: LoaderEntries overwritten by repeated same-command calls (blsuki.c) ==

Discovery:
Observation from the first pass, promoted after the follow-up pass pointed out the concrete call sequence.

Source trace:
- blsuki_cmd() blsuki.c 1762-1804: `entries = NULL;` at line 1772 before blsuki_load_entries(); the list is rebuilt
  from the directory on every call; entries are allocated with grub_zalloc (639), so `visible` starts false.
- blsuki_create_entries() 1723-1759 marks `entry->visible = true` (1748) only for entries it creates in this call,
  filtered by --show-default / --show-non-default / --entry (1738-1740).
- set_bli_loader_entries() lists only `entry->visible` entries (1522, 1575). The previous LoaderEntries value is
  read only if the OTHER command's flag is "1": blscfg reads GRUB_BLSUKI_ENTRIES_UKI (1547), uki reads
  GRUB_BLSUKI_ENTRIES_BLS (1549); the own flag is only written (1708, 1710) and never consulted.
- Sequence: `blscfg --show-default` -> LoaderEntries = {default entry}; `blscfg --show-non-default` -> new list, the
  default entry is neither created nor visible, no merge (UKI flag unset) -> LoaderEntries = {non-default entries},
  the default entry (which is in the menu) is gone. Likewise `blscfg -e A` then `blscfg -e B` leaves only B.
- docs/grub.texi 7245-7270 documents the three options as filters for which entries are added to the menu, so
  calling blscfg more than once with different filters is the documented use. No in-tree script does this
  (`rtb grep blscfg -- util` finds nothing).
- The BLI page (fetched, model-summarised): LoaderEntries "may be used to let the OS know which boot menu entries
  were discovered by the boot loader", listed "in the order the entries are shown on screen".

Consequence:
After the second call the variable no longer matches what is on screen; the first call's entries are not advertised.

Fix assessment:
No draft diff. Also consulting the command's own flag would merge, but the merge compares the stored (canonical)
id with `entry->filename` (1641), which still has the counter and, for UKI, the extension, so the duplicate check
(rc == 0 only for identical strings) would miss re-added entries or, for plain names, abort with "duplicate file".
A correct fix needs the canonical-id helper from Issue 5 first.

-- Fresh read of the unchanged / trivially changed code (Issues 5 and 6 came out of the follow-up pass) --
- set_bli_loader_entries (blsuki.c 1507-1718): buffer arithmetic. Allocation = 2*size + prev_start_size bytes;
  remaining_size starts at size + prev_start_size/2 units and is decreased by exactly the units written (new
  entries: written+1 <= len+1, checked against remaining_size first; previous entries: len16+1). The leftover
  append copies prev_entries_size bytes with remaining_entries_size <= remaining_size; with an odd trailing byte
  that is 2*remaining+1 bytes, which is exactly the slack the allocation still has, so no overflow. An odd-sized
  variable that is consumed unit by unit ends in the "malformed LoaderEntries variable" error, not an overread.
- UTF-8 buffers: grub_utf16_to_utf8 (charset.h 201-) emits at most 4 bytes per UTF-16 unit (3 for BMP, 4 per
  surrogate pair of 2 units, 1 for '?'), and GRUB_MAX_UTF8_PER_UTF16 is 4 (charset.h 39), so size16*4+1 (bli.c
  199-211, blsuki.c 1623) always holds the result plus NUL; grub_mul/grub_add guard the arithmetic.
- get_efivar: grub_efi_get_variable_with_attributes initialises *data_out = NULL and *datasize_out = 0 up front
  (efi.c 226-227), so reading `size` before the status test is defined; val_efi is freed once at `finish`.
- grub_malloc(0) returns a valid block here (mm.c grub_memalign: n = ((size + ALIGN - 1) >> LOG2) + 1), so an
  empty LoaderEntries does not trip the `efi_entries == NULL` check.
- bls_create_entry: id_dup is freed at finish (blsuki.c 1144); grub_normal_add_menu_entry strdups the id
  (menuentry.c, `menu_id = grub_strdup (id ? : menu_title)`), so there is no use after free. grub_error_push/pop
  around grub_strtol() preserves the caller's errno.
- blsuki_add_entry ordering (commit 7): the override only fires when exactly one of the pair has 0 tries left, so
  non-zero entries are inserted before the first 0-tries entry and a 0-tries entry stays after all others; both at
  0 fall back to filevercmp.
- bls_bumpcounter buffer bound (commit 10): size_info = offsetof(FileName) + 512 bytes; GetInfo is offered
  size_info-4; destination capacity for grub_utf8_to_utf16 is (size_info - offsetof)/2 units (loop stops at
  destsize, charset.h 125-); len16 >= capacity bails; otherwise the NUL at index len16 is in range. After a
  BUFFER_TOO_SMALL retry, size_info = size+4, i.e. two more UTF-16 units than the old name needs. Not reported:
  an astral character that does not fit makes grub_utf8_to_utf16 stop one unit early, so the check passes and a
  truncated name would be written; unreachable for realistic ~250-character BLS names. (The overflow branch of the
  same retry has the double free reported as Issue 2 item 4.)
- run_menu "disabled" style: handled in the same early-return as timeout == 0 (menu.c 707-713), so it behaves like
  an existing timeout=0 configuration; get_timeout_style() maps the new name.
- file_info->Size is not updated after the name changes and SetInfo gets the buffer size (not reported: I have no
  in-tree or independently checked reference for what firmware expects; a WebFetch summary of systemd's
  boot_entry_bump_counters describes the same behaviour, which I did not verify further).
