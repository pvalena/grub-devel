What the patch does
-------------------
Before: get_devargs used grub_strrchr(path, ':') for every path (no NVMe-oF handling). get_devname used
grub_strchr(path, ':') (first colon), then overrode `colon` for paths containing "nvme-of": the first colon after
"/namespace@", or NULL when there is no "/namespace@".
After: grub_ieee1275_find_colon_separator() does strrchr first (NULL -> NULL), then the same nvme-of override
(first colon after "/namespace@", else NULL). Both callers use it; get_devargs returns
colon ? grub_strdup(colon + 1) : NULL; get_devname keeps its alias lookup and strndup tail unchanged.
No allocation happens in the helper, so no new leak or ownership question; no pointer is dereferenced before a
NULL test (colon is tested in both callers, namespace_split before strchr).
The nvme-of override cannot produce a pointer outside the string: grub_strchr(namespace_split, ':') searches from
inside `path`. If strrchr found no colon, nvme-of paths also have none after "/namespace@" (a colon after it would
also be a last-colon candidate), so the early NULL return equals the override result.

Traced inputs (old devname / old devargs -> new devname / new devargs)
----------------------------------------------------------------------
A. "/vdevice/v-scsi@30000067/disk@8100000000000000:2,\grub.elf" (single colon, not nvme-of)
   old: ".../disk@8100000000000000" / "2,\grub.elf"; new: identical.
B. "/nvme-of/controller@500a098000000001,ffff:nqn=nqn.2014-08.org.nvmexpress:uuid:abc/namespace@1:2,\grub.elf"
   (format matches the builders at ofdisk.c:514/544 and ofpath.c:806/813)
   old devname: nvme-of branch -> first colon after "/namespace@" -> ".../namespace@1"; old devargs: last colon
   of the whole path = the one after "namespace@1" -> "2,\grub.elf". New: identical for both.
C. Same as B without ":2,\grub.elf" (bootpath naming the whole namespace)
   old devname: whole path; old devargs: last colon is inside the NQN -> "abc/namespace@1" (non-NULL garbage).
   new devname: whole path; new devargs: NULL. This is the intended consistency fix.
D. B with a colon inside the arguments: "...namespace@1:2,\EFI:x"
   old devargs: last colon -> "x" (wrong); new: first colon after "/namespace@" -> "2,\EFI:x".
E. Non-nvme-of path whose argument field contains a colon, e.g. "/pci@f4000000/ata-6@d/disk@0:3,\:tbxi"
   old devname: first colon -> ".../disk@0"; new devname: last colon -> ".../disk@0:3,\" (includes the args).
   devargs is "tbxi" both before and after (strrchr). So devname becomes inconsistent with the first-colon rule it
   used before; the commit message documents the new rule ("otherwise, use the final colon in the path").
   Reachability: I found no producer of such paths in this tree. ofnet.c SUFFIX (":speed=auto,duplex=auto,1.1.1.1,
   ..."), the ofpath.c formats (all "...:%c" / "...:%d" with one colon) and sparc obdisk.c (strip_ob_partition cuts
   at the first colon before get_devname is called, so its input has no colon) are all single-colon. Whether
   firmware bootpaths for other device types (IPv6 network arguments, Apple-style ",\:tbxi" file arguments) take
   this shape was not checked, so this is recorded as an observation, not an issue.
F. No colon at all: helper returns NULL; devname uses pathlen = strlen(path); devargs NULL. Unchanged.
G. PCIe NVMe "/pci@.../nvme@0/namespace@1:2,\boot" (path builder at ofdisk.c:633 appends "/namespace@%x" to the
   controller path): does not contain "nvme-of", exactly one colon, so it takes the plain last-colon branch and
   gives the same result as before for both functions.

Pre-existing, not introduced here
---------------------------------
parse_args() early `return 0` when args == NULL skips `grub_free (device)` (the strdup'd/alias name returned by
get_devname); the comment says "Shouldn't happen". Case C is now a legitimate input that takes this path (before,
non-NULL garbage args avoided it; for the example in C the garbage "abc/namespace@1" reaches encode_devname as
partition "1bc/namespace@1" and fails strtoul with "invalid partition number").
Leak is one short string once per boot and the early return already existed for colon-less paths, so it is noted
here only.
