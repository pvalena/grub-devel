# AI Review: MR !324 - diskfilter: Fix partmaps leak and harden RAID10 validation and size calculation

2 commits in `grub-core/disk/diskfilter.c`: a GRUB_UTIL-only fix freeing the per-entry `pv->partmaps` strings in
`free_array()`, and RAID10 hardening (`validate_segment()` checks, overflow-checked size in
`grub_diskfilter_make_raid()`). Listed in apply order; the two commits touch unrelated functions.

**Commits:**
1. **3e484e552** - diskfilter: Fix GRUB_UTIL partmaps memory leak
2. **35c505ae6** - diskfilter: Harden RAID10 validation and size calculation

## Issues Found

### Issue 1: RAID10 validation still accepts `far == 0` for offset layouts, so reads can succeed without reading

**Location:** `grub-core/disk/diskfilter.c`, `validate_segment()`, line 594; `read_segment()`, lines 679-753

After this MR the check is `if (near == 0 || ((seg->layout >> 16) == 0 && far == 0))`, so `far == 0` is still accepted
whenever any bit at or above bit 16 is set. Example: layout `0x10002` (near = 2, far = 0, offset flag). It passes
`grub_diskfilter_make_raid()` (`n = near = 2`, so the `n == 0` test at 1153 does not fire), passes `validate_segment()`,
and `is_lv_readable()` needs only `node_count - near + 1` members (one, when `node_count == near == 2`).

In `read_segment()` the offset branch sets `ofs = far = 0` (683-684), so the `for (j = 0; j < far; j++)` loop (715)
never runs, `err` stays 0, `if (! err) break;` (736) leaves the `i` loop, and the function advances `buf` and `size` and
finally returns `GRUB_ERR_NONE` (750-753) without ever writing `buf`. There is no out-of-bounds access: each pass of
the outer loop consumes at least one sector (`read_size = stripe_size - b`, `stripe_size` is validated non-zero), so
it terminates. The layout is an on-disk 32-bit field passed unchecked from `mdraid_linux.c:262` and
`mdraid1x_linux.c:290`, the only producers that pass level 10 (`dmraid_nvidia.c` builds levels 0/1/5), so a crafted
md superblock supplies it.

Consequence (read from source, nothing run): the driver reports success and the caller gets uninitialised data.
`grub_disk_read_small_real()` allocates `tmp_buf` with `grub_malloc` (`kern/disk.c:448`), calls the driver (458), copies
`tmp_buf` to the caller (465) and stores it in the disk cache (466); larger reads go straight into the caller's buffer
and are cached too (`disk.c:606-615`). Heap residue is then served, and cached, as the contents of the volume.

The tree already treats `far == 0` as invalid: `grub_diskfilter_make_raid()` rejects `near == 1, far == 0`
(1150-1157) and `validate_segment()` rejects it for non-offset layouts, where `read_segment()` would divide by
`far * stripe_size` (687-688). This MR rewrites exactly this condition and its commit message targets the same
"skips all read attempts while still reporting success" symptom for `near == 0`, so the offset case is the
remaining gap. The commit message says the
existing validation for non-offset layouts with `far == 0` is preserved; it does not mention offset layouts.

**Draft fix** -- reject `far == 0` regardless of the offset flag:

```diff
--- a/grub-core/disk/diskfilter.c
+++ b/grub-core/disk/diskfilter.c
@@ validate_segment (struct grub_diskfilter_segment *seg, unsigned int depth)
-	if (near == 0 || ((seg->layout >> 16) == 0 && far == 0))
+	if (near == 0 || far == 0)
 	  return grub_error (GRUB_ERR_BAD_FS, "invalid segment");
```

Whether Linux md can ever write `far == 0` with the offset flag is not checkable from this tree; if it can, such an
array would now be rejected instead of being read without any copy being fetched.

## Additional findings

`near == 0` is a runtime no-op for current callers: `grub_diskfilter_make_raid()` already returns NULL for it
(`n == 0`, diskfilter.c:1150-1157) and md is the only RAID10 producer, so `far > node_count` is the only new rejection.
The partmaps fix is consistent (NULL-terminated array, zalloc'd `pv`, callbacks only borrow the strings); the re-insert
path at :1367 still overwrites `partmaps` without freeing it (pre-existing, not covered by this MR).
