== Commit 1: DHCP Infinite Loop Fix (9c4394cce) ==

Fix: Add in_extra flag to prevent infinite loop in find_dhcp_option().

Verification:
RFC 2131 section 4.1 states the OVERLOAD option (tag 52) is only valid in the main options field. The
pre-patch code processed OVERLOAD even while scanning overloaded boot_file/server_name fields. A crafted
boot_file containing \x34\x01\x03 (OVERLOAD=3) would make "goto again" re-enter boot_file forever.

Read find_dhcp_option() at lines 215-345. The in_extra flag is:
- Initialized to 0 at function entry (line 220)
- Set to 1 at lines 323, 333 when entering boot_file or server_name processing
- Used to guard OVERLOAD processing at line 282: "if (tagtype == ... && !in_extra)"

The end variable is correctly reset to 0 at line 315 before each "again" jump, so each field must have its
own END tag.

Trace example: packet with main options ending in OVERLOAD=1 (file field), and boot_file containing
OVERLOAD=1. First pass: in_extra=0, OVERLOAD processed, overload=1. Second pass (boot_file): in_extra=1,
OVERLOAD ignored, no loop. Correct.


== Commit 2: DHCP String Bounds (774f65209) ==

Fix: Replace grub_strndup with explicit-length memcpy for server_name and boot_file.

Verification:
Read grub_net_configure_by_dhcp_ack() at lines 450-510. The server_name and boot_file strings come from
DHCP options and are not NUL-terminated (raw option data). grub_strndup internally calls grub_strlen,
which scans for '\0' and would read past the option boundary if no terminator is present.

Lines 465-471 (server_name): grub_malloc(server_name_len + 1), grub_memcpy with explicit length,
manual NUL termination. Lines 477-489 (boot_file): same pattern.

Lines 475, 477: grub_xasprintf uses %.*s with (int)server_name_len as precision specifier, which limits
the read. Correct.

The fix prevents heap buffer over-reads when fuzzing supplies non-terminated option data.

free nb on chunk handling errors.

- Line 122: 404 "file not found"
- Line 130: "unsupported HTTP error %d"

ERROR handling (lines 275-281): Checks packet is at least opcode + errcode + 1 byte (line 275). Then
line 281 forces NUL-termination at nb->tail - 1. Since nb->tail - nb->data >= 5 at this point,

== Commit 8: UDP/BOOTP Header Checks (724a7367e) ==

Fix: Check datagram length before reading UDP and BOOTP headers in DHCP fast-paths.

Verification:
Read handle_dgram() at lines 240-365. The DHCP fast-paths read packet headers without checking length.

Lines 260-262: have_udp is set to true only if proto == GRUB_NET_IP_UDP AND the datagram is at least
sizeof(struct udphdr) bytes. This check happens before any UDP header access.

Line 264: DHCP6 fast-path (port 546) now guarded with "if (have_udp && ...)". Line 306: DHCPv4 fast-path
(port 68) also guarded with "if (have_udp && ...)".

Lines 336-342: After pulling the UDP header, the code checks if the remaining data is at least
sizeof(struct grub_net_bootp_packet) before casting nb->data to bootp and reading bootp->mac_addr (line
347, inside FOR_NET_NETWORK_LEVEL_INTERFACES).

Without these checks, a UDP datagram with no payload (IPv4 packet whose total length covers only the IP
header) would leave nb empty after the IP header is pulled, yet handle_dgram() would cast nb->data to
struct udphdr and read udph->dst. Likewise, the BOOTP path would read bootp->mac_addr without verifying
the full BOOTP packet is present. Both are OOB reads, prevented by the added checks.


== Commit 9: DNS Empty Reply (59519902a) ==

Fix: Return error immediately when DNS lookup succeeds but naddresses == 0.

Verification:
Read grub_net_resolve_address() at lines 585-612. When grub_net_dns_lookup() succeeds (err == GRUB_ERR_NONE)
but returns naddresses == 0, the pre-patch code called grub_error() at line 606, then fell through to
"*addr = addresses[0]; ... return GRUB_ERR_NONE;" at lines 611-613.

addresses is allocated with grub_calloc(ancount, ...) in recv_dns_packet(). When ancount == 0 (a
well-formed DNS reply from a malicious server with zero answer records), addresses is a zero-element
allocation. addresses[0] reads one sizeof(grub_net_network_level_address_t) past the end - a heap buffer
over-read.

The fix at lines 606-607 uses "return grub_error(...)" instead of just calling grub_error(), so the error
is returned immediately without falling through to the OOB read. Correct.


== Commit 10: net_add_route Uninitialized Variable (0b5f84811) ==

Fix: Check return value of grub_net_resolve_net_address() in grub_cmd_addroute().

Verification:
Read grub_cmd_addroute() at lines 1297-1320. The target variable is declared uninitialized at line 1299.
Line 1307 calls grub_net_resolve_net_address(args[1], &target).

grub_net_resolve_net_address (not shown, but similar to grub_net_resolve_address) parses args[1] as an
IPv4/IPv6 network address. If it fails (bad address), it returns grub_error() without writing to *addr.

Pre-patch: The return value was not checked. If the parse failed, target remained uninitialized. The code

uninitialized stack memory.

The fix at lines 1308-1309 checks "if (err) return err;", preventing use of uninitialized target. The
gw-address handling three lines below (line 1314) already had this check - the fix brings target handling
to parity.


== Commit 11: EFI efinet NULL Pointer Dereferences (3d3e423d6) ==

Fix: Guard all ldp dereferences with NULL checks.

Verification:
Read grub_efinet_create_dhcp_ack_from_device_path() at lines 475-670. The function calls
grub_efi_find_last_device_path(ddp) five times, each time assigning the result to ldp and then
dereferencing it.

grub_efi_find_last_device_path returns NULL when the device path starts with an END_ENTIRE node (i.e.,
empty path). This is structurally valid - firmware or an HTTPBoot driver can hand GRUB such a path.

Pre-patch dereferences without NULL checks:
- Line 490: GRUB_EFI_DEVICE_PATH_TYPE(ldp) - macro dereferences ldp->type
- Line 518: Same, inside "if (GRUB_EFI_DEVICE_PATH_TYPE(ldp) == ...)"
- Line 529: Same
- Line 654: while loop checking ldp type/subtype
- Line 664: if checking ldp type/subtype for MAC address

The fix adds NULL checks:
- Lines 488-490: "if (!ldp || GRUB_EFI_DEVICE_PATH_TYPE(ldp) != ...)"
- Lines 518-520: "if (ldp && GRUB_EFI_DEVICE_PATH_TYPE(ldp) == ...)"
- Lines 529-531: "if (!ldp || ...)"
- Lines 654-656: "while (ldp && ...)"
- Lines 664-666: "if (ldp && ...)"

All five ldp usage sites are now guarded. NULL paths fall through to grub_free(ddp); return NULL;


== Commit 12: IPv6 Parse Uninitialized Memory (483336854) ==

Fix: Decrement word when no hex group is parsed, reject word > 7.

Verification:
Read parse_ip6() at lines 475-530. The for loop at line 479 parses up to 8 hex groups into newip[word].

Issue 1: When grub_strtoul fails (line 490, grub_errno set), no group was parsed - ptr points to a
non-hex-digit character (e.g., "::" with nothing after, or a trailing ":""). At this point, word has
already been incremented by the for loop's own increment (happens before the body runs in the next
iteration check). newip[word] was never written. Pre-patch: just cleared grub_errno and broke. Post-loop
code treats indices [quaddot, word] as containing real parsed groups. If word points to an uninitialized
slot, the memmove at line 528 copies garbage.

The fix at line 498 decrements word before breaking, undoing the for loop's increment. Now word points to
the last successfully parsed group. Correct.

Issue 2: word can reach 8 when input is "1:2:3:4:5:6:7:8:" (colon trailing the 8th group). The group
itself is parsed and stored at newip[7] via the "break" at line 502. The for loop's increment then pushes
word from 7 to 8, and "word < 8" is false, so the loop exits normally (not via break). This is invalid
IPv6 (every ':' must be followed by another hex group or a second ':'), but nothing above rejects it.

At line 528, quaddot != -1 triggers "grub_memmove(&newip[quaddot + 7 - word], ...)". With word == 8,
"7 - word" is -1. As the third argument to grub_memmove (size_t, unsigned), this becomes 0xFFFFFFFF... -
a multi-exabyte memset, stack-smashing write.

The fix at lines 511-513 rejects word > 7, preventing the huge memset. Correct.

== Commit 14: ICMPv6 Option Header Bounds (fd7318b7e) ==

Fix: Require full option header before dereferencing ohdr->len.

Verification:
Read grub_net_recv_icmp6_packet() at lines 215-410. Three option walks appear: neighbour solicit
(lines 225-227), neighbour advertise (lines 334-336), router advertise (lines 388-390).

Pre-patch loop condition: "ptr < nb->tail" - only proves one byte remains.
struct option_header is two bytes: { grub_uint8_t type; grub_uint8_t len; }.

When an option starts on the final byte of the packet, ptr == nb->tail - 1. The loop condition
"ptr < nb->tail" is true (one byte remains). Inside the loop, line 229 (or 338, 394) dereferences
ohdr->len - reads the second byte of the struct, which is one byte past the received data (at nb->tail).

The len value is adjacent heap memory, not packet content. It cannot push the walk further out of bounds:
the check at line 230 (or 339, 395) "if (ohdr->len == 0 || ptr + 8 * ohdr->len > nb->tail)" rejects
len == 0 and any len that would walk past nb->tail. So the loop exits either way. But the ohdr->len read
itself is still OOB.

The fix changes the loop condition to:
  "ptr + sizeof(struct option_header) <= nb->tail"

This requires both bytes of the option header to be present before the loop body runs, so ohdr->len is
always in bounds. All three walks use identical fix. Correct.


== Commit 15: IP send_fragmented Netbuff Leak (f49b237da) ==

Fix: Free nb2 after each send and on all error paths.

Verification:
Read send_fragmented() at lines 125-195. The function sends a large IP packet as fragments. Each fragment
is built in a new netbuff nb2.

Pre-patch: nb2 was declared inside the while loop at line 141. It was allocated at line 145, used to build
and send the fragment, but never freed. send_ethernet_packet() does not take ownership (the comment at
lines 187-188 confirms this). Every fragment sent leaked one netbuff. Error paths (lines 151, 154, 174,
177, 180, 183) returned directly without freeing nb2.

The fix:
- Line 133: Declare nb2 at function scope, initialized to NULL
- Lines 153, 156, 175, 179, 182, 185: All error paths now "goto fail;" instead of returning directly
- Lines 188-189: After successful send, free nb2 and set it to NULL
- Lines 193-195: fail label frees nb2 (safe with NULL) and returns err

The nb2 = NULL at line 189 is necessary: after freeing nb2 at the end of one iteration, if the next
iteration allocates nb2 and then hits an error, "goto fail" would double-free if nb2 still held the old
pointer. Setting it to NULL prevents this.

All fragments now freed. Leak eliminated.
