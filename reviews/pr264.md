# AI Review: MR !264 - Avoid busy polling for UEFI and BIOS console input; use PAUSE in x86 idle

**Re-review**: 3 commits now (was 1). The original UEFI commit (was 2d5353490, now 77ce527b1) is unchanged: identical
patch and message, only rebased on a newer `origin/master`. Two new commits: 35f424df1 (PAUSE in `grub_cpu_idle()`)
and b97169739 (BIOS console wait plus native test). None dropped.

Two commits stop `grub_getkey()` from spinning at a prompt, via an optional `wait` terminal callback (EFI event wait
with a 20 ms timer; INT 15h/AH=86h for the PC BIOS console). The PAUSE commit still spins; it only adds a spin-wait
hint to each `grub_cpu_idle()` iteration (its message says the benefit was not measured), also in the fallback path.

## Additional findings

The EFI and BIOS callbacks share one gate in `grub_getkey()` (single active input, no native USB polling) and a sticky
`input_wait_failed` reset by `.init`. PAUSE is a runtime no-op for `GRUB_UTIL`/emu builds (empty `grub_cpu_idle()` in
`include/grub/time.h`); the in-tree callers are all spin loops. The `console.c` include rewrite and `regparm(3)` limit
are equivalent on i386-pc. Caveats: physical BIOS untested (author-stated); the BIOS wait requests 20 ms but the actual
duration is firmware-dependent. Hygiene: `.gitignore` has no entries for the two new test binaries (not a failure).
