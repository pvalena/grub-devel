## Additional findings

Traced both scenarios this function's peeling sequence (strip URI, then DNS, then IPv4/IPv6,
then VLAN, each via a fresh `grub_efi_find_last_device_path()` call) is meant to handle:

- edk2 HTTP-boot style path ending directly in an IPv4/IPv6 pseudo-node (no URI/DNS wrapping):
  the first two checks no-op (the last node is neither URI nor DNS), so the new conditional
  IPv4/IPv6 check fires exactly as the old unconditional code did — no behavior change.
- The iPXE path this MR fixes (`.../MacAddr(...)/Uri(...)`): the URI check strips the URI node,
  leaving the MAC node as the new last node. Before this patch, the next block unconditionally
  stripped that MAC node too, so the rebuilt path could never match the physical SNP card's
  path. Now the MAC node's subtype is neither IPv4 nor IPv6, so it is correctly left in place.

The four peeling blocks (including the two untouched by this diff) dereference
`grub_efi_find_last_device_path()`'s result without a NULL check, unlike the analogous loop in
`grub-core/disk/efi/efidisk.c`'s `grub_efidisk_get_device_name()`, which does check. This is
unchanged by this patch (the modified block already dereferenced unconditionally before the fix)
and is only reachable if a matched device path had no node preceding the stripped one (e.g. a
path consisting of a bare URI node with nothing before it) -- not reachable via any
spec-conforming firmware's SNP-derived path, which is always rooted in a hardware node before a
MAC/URI node; not a regression introduced here.
