# AI Review: MR !218 - grub-install: force journal draining to ensure data integrity

Note: older base (not rebased onto current `origin/master`); reviewed via the merge-base diff.

1 commit adding `grub_install_sync_fs_journal()` (Linux `FIFREEZE`/`FITHAW`, no-op stub on other hosts), called from
grub-install for xfs/ext2 boot filesystems, plus a `fsfreeze`-based `sync_fs_journal()` in grub-mkconfig.

**Commits:**
1. **9c902969c** - grub-install: force journal draining to ensure data integrity

## Issues Found

### Issue 1: grub-mkconfig builds the grub.cfg path from `@PACKAGE@` instead of `@grubdirname@`

**Location:** `util/grub-mkconfig.in`, `sync_fs_journal()`, lines ~325 and ~330

`grub_cfg_rel_path` is `/boot/@PACKAGE@/grub.cfg` (or `/@PACKAGE@/grub.cfg` for a separate /boot) and is compared
with `make_system_path_relative_to_its_root "$grub_cfg"`. In this tree `@PACKAGE@` is only used for the data
directory and `TEXTDOMAIN`; the GRUB directory is `@grubdirname@` (`--with-grubdir`, defaulting to `$PACKAGE` at
`configure.ac:344`), as in `grub-reboot.in`, `grub-set-default.in` and `00_header.in`, and as grub-install itself
uses via `GRUB_DIR_NAME`. `PACKAGE` comes from `AM_INIT_AUTOMAKE` and is not changed by `--with-grubdir`.

On a build with a non-default `--with-grubdir` (e.g. `grub2`), the conventional distro output path
`-o /boot/grub2/grub.cfg` yields `/boot/grub2/grub.cfg`, which never equals `/boot/grub/grub.cfg`, so the test
fails and the grub-mkconfig half of the feature silently never runs. The grub-install half is unaffected (it uses
`grubdir` directly).

Holds on both the pr218 base and current `origin/master` (same `configure.ac` and sibling scripts).

**Draft fix** -- use the configured directory name:

```diff
--- a/util/grub-mkconfig.in
+++ b/util/grub-mkconfig.in
@@ sync_fs_journal () {
   boot_fs="$GRUB_FS"
-  grub_cfg_rel_path="/boot/@PACKAGE@/grub.cfg"
+  grub_cfg_rel_path="/boot/@grubdirname@/grub.cfg"
   mount_point="/"
@@
-    grub_cfg_rel_path="/@PACKAGE@/grub.cfg"
+    grub_cfg_rel_path="/@grubdirname@/grub.cfg"
     mount_point="/boot"
```

### Issue 2: Only SIGINT and SIGTERM are blocked while the filesystem is frozen

**Location:** `grub-core/osdep/linux/journaled_fs.c`, `grub_install_sync_fs_journal()`, lines ~43-46;
`util/grub-mkconfig.in`, `sync_fs_journal()`, line ~335

The function blocks only `SIGINT` and `SIGTERM` between `FIFREEZE` and `FITHAW`, so that an interrupted
grub-install cannot leave the filesystem frozen. grub-install installs no signal handlers, so an unblocked
`SIGHUP` (for example an ssh session dropping) or `SIGQUIT` that arrives while `FIFREEZE` is running stays pending
and terminates the process as soon as the ioctl returns, before `FITHAW` is issued. A freeze persists after the
freezing process exits (the shell variant in the same commit relies on this: it freezes and thaws from two
different processes), so every writer on that filesystem then blocks until someone runs `fsfreeze --unfreeze`.
Stop signals (`SIGTSTP`, `SIGTTIN`, `SIGTTOU`) are also unblocked, so Ctrl-Z inside the window would likewise leave
the filesystem frozen until the job is resumed. The shell variant ignores `HUP INT TERM` (which shows the intent)
but omits `QUIT` too, so on this branch a SIGQUIT between `fsfreeze --freeze` and `--unfreeze` kills the shell.
The window is narrow, but the failure is a hung system and the fix is small. I did not reproduce this; it follows
from default signal dispositions and the code above.

**Draft fix** -- block every blockable signal for the freeze window, and add `QUIT` to both `trap` lines:

```diff
--- a/grub-core/osdep/linux/journaled_fs.c
+++ b/grub-core/osdep/linux/journaled_fs.c
@@ grub_install_sync_fs_journal (const char *path)
-  sigemptyset(&set);
-  sigaddset(&set, SIGINT);
-  sigaddset(&set, SIGTERM);
-  sigprocmask(SIG_BLOCK, &set, &old_set);
+  /* Keep all blockable signals pending until the filesystem is thawed.  */
+  sigfillset (&set);
+  sigprocmask (SIG_BLOCK, &set, &old_set);
```

```diff
--- a/util/grub-mkconfig.in
+++ b/util/grub-mkconfig.in
@@ sync_fs_journal () {
-    trap '' HUP INT TERM
+    trap '' HUP INT QUIT TERM
     fsfreeze --freeze "${mount_point}" && fsfreeze --unfreeze "${mount_point}"
-    trap - HUP INT TERM
+    trap - HUP INT QUIT TERM
```

## Additional findings

`restore_backup_atexit()` (`util/grub-install-common.c` ~292-349) unlinks the `name~` backups via `atexit()`, i.e.
after `main()` returns and therefore after the new freeze/thaw (`util/grub-install.c` ~2045-2077), so the drain is
not strictly the last filesystem activity (same on current `origin/master`). GRUB never reads the `name~` names, and
its XFS/ext2 drivers read on-disk metadata without replaying a log, so no failing input is shown. If the author wants
the drain strictly last, registering the sync with `atexit()` at the start of `main()` makes it run after the
backup handler.
