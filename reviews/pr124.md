### Issue 1: `.conf` default is never matched, `val_dup` is unused (menu.c)

**Location:** `grub-core/normal/menu.c`, `get_entry_number()`, lines ~554-568 (commit 2)

The rework of the const-mutation issue allocates a copy of the value without the suffix, but still compares
against the original `val`:

```c
val_dup = grub_strndup(val, ext - val);
if (val_dup)
  {
    res = menuentry_eq (e->id, val);      /* val, not val_dup */
    grub_free (val_dup);
  }
if (res)
```

`menuentry_eq (e->id, val)` is the exact call the loop made a few lines earlier
(`menuentry_eq (e->title, val) || menuentry_eq (e->id, val)`, line 548) and that already failed for this entry,
so `res` is always 0 and the new block is dead. A `default` of `foo.conf` (the form commit 2 is written to
accept) never selects the entry with id `foo`; the first menu entry boots instead, which defeats the purpose of
commit 2. Also, `res` (line 527) is never initialised:
if `grub_strndup()` fails, `if (res)` reads an indeterminate value.

**Draft fix** -- compare the stripped copy and initialise `res`:

```diff
--- a/grub-core/normal/menu.c
+++ b/grub-core/normal/menu.c
@@ get_entry_number
 	      if (ext && grub_strcmp (ext, ".conf") == 0)
 		{
+		  res = 0;
 		  val_dup = grub_strndup(val, ext - val);
 		  if (val_dup)
 		    {
-		      res = menuentry_eq (e->id, val);
+		      res = menuentry_eq (e->id, val_dup);
                       grub_free (val_dup);
 		    }
 		  if (res)
```

### Issue 2: Leaks and a double free in `grub_cmd_bls_bumpcounter()` (bls_bumpcounter.c)

**Location:** `grub-core/commands/bls_bumpcounter.c`, `grub_cmd_bls_bumpcounter()`, lines 149-167, 198-281
(commits 5 and 10)

1. The `grub_strdup (blsdir)` copy (line 160, added to avoid mutating the env value) is never freed: not on the
   `Open` failure return (line 180), not on the success returns (272, 276), not at `finish`. One leak per call
   whenever `blsdir` is set.
2. `new_path` (allocated in `bump_counter()`, line 226) is freed only on the success path (line 262). The two
   exits `goto finish` at line 245 (new name too long) and line 254 (`SetInfo` failed) leak it.
3. The volume root handle from `volume->OpenVolume (volume, &root)` (line 149) is never closed on any path (there
   is no `root->Close`), one unbalanced firmware handle per call.
4. Double free of `file_info`: line 200 frees it in the `GRUB_EFI_BUFFER_TOO_SMALL` branch without clearing the
   pointer. If `grub_add (size, 4, &size_info)` then overflows (line 204, the check added by commit 10), line 207
   jumps to `finish`, which frees the same pointer again (line 280). Trigger: `GetInfo` reporting a required
   size within 4 of 2^64, i.e. only a corrupt firmware answer, but it is the very path the new check handles.

Lines 269-273 are dead (`err` is still `GRUB_EFI_SUCCESS` there) and can be dropped.

### Issue 3: A `+` that is not a boot counter leaves `GRUB_ERR_BAD_NUMBER` set (bls_bumpcounter.c)

**Location:** `grub-core/commands/bls_bumpcounter.c`, `bump_counter()`, lines 56-91; caller `menu.c:321` (commit 5)

`grub_cmd_bls_bumpcounter()` treats any `+` in its argument as a counter (line 124). The argument is
`blsuki->filename` as passed by `menu.c:321`: the file name without `.conf`, counter kept if present. Yet
`bls_create_entry()` (commit 11) and `tries_left()` (commit 7) deliberately treat a non-numeric `+` as "no
counter" (e.g. a kernel version such as `fedora-6.8.0-rc1+`). For such a name `grub_strtol ("")` fails with
`GRUB_ERR_BAD_NUMBER`,
`bump_counter()` returns NULL (line 81) without clearing it, the command returns `GRUB_ERR_BUG`, and
`grub_menu_execute_entry()` ignores the result. The stale error is then printed by the script executor after the
entry's first command (`execute.c:1120`) as `error: unrecognized number.`, and because the printed-error counter
changed, `menu.c:329-330` calls `grub_wait_after_message()` ("Press any key to continue...", up to 10 s) on every
boot of that entry. The same leak happens when only the second number is malformed (`+3-x`, lines 76-78): `tries`
is reset to -1 but the error stays set while the rename proceeds and the command returns `GRUB_ERR_NONE`.

**Draft fix** -- clear the expected parse failure where it is handled:

```diff
--- a/grub-core/commands/bls_bumpcounter.c
+++ b/grub-core/commands/bls_bumpcounter.c
@@ bump_counter
 	  if (grub_errno == GRUB_ERR_NONE)
 	    {
 	      tries++;
 	    } else {
+	      grub_errno = GRUB_ERR_NONE;
 	      tries = -1;
 	    }
 	}
     } else {
+      /* '+' not followed by a number, e.g. "...-6.8.0+": not a boot counter */
+      grub_errno = GRUB_ERR_NONE;
       return NULL;
     }
```

### Issue 4: `LoaderFeatures` is still written through a `long` (bli.c)

**Location:** `grub-core/commands/bli.c`, `set_loader_features()`, lines 51-63 (commit 6)

The rework switched the flag constants to `1ULL` and the size argument to `sizeof(loader_features)`, but the
variable is still `static long loader_features`, so the written size is `sizeof(long)`: 4 bytes on i386-efi,
arm-efi and riscv32-efi (the `bli` module has `enable = efi`, which covers them; `gentpl.py:55`). The Boot
Loader Interface defines `LoaderFeatures` as a 64-bit unsigned integer (systemd.io/BOOT_LOADER_INTERFACE).

**Draft fix:**

```diff
--- a/grub-core/commands/bli.c
+++ b/grub-core/commands/bli.c
@@ set_loader_features
-  static long loader_features =
+  static grub_uint64_t loader_features =
```

### Issue 5: Advertised `LoaderEntries` ids differ from the menu ids for UKI and non-numeric-`+` entries

**Location:** `grub-core/commands/blsuki.c`, `set_bli_loader_entries()` lines 1520-1538 and 1573-1590,
`uki_create_entry()` lines 1156/1219, `bls_create_entry()` lines 1034-1082; `grub-core/normal/menu.c`,
`get_entry_number()` lines 554-568 (commit 1, unchanged since the prior round, and commit 2)

`set_bli_loader_entries()` builds each advertised id from `entry->filename` by cutting at the last `+` (whatever
follows it) or else dropping `.conf`/`.efi`. The menu ids are built differently:

1. `uki_create_entry()` passes `id = entry->filename` unchanged (lines 1156, 1219; the same name is used in the
   `chainloader` path at line 1215), so the menu id of `fedora-6.8.0.efi` keeps `.efi`, while `LoaderEntries`
   lists `fedora-6.8.0`.
2. `bls_create_entry()` removes a `+` suffix only when it is numeric (lines 1042-1076), so `fedora-6.8.0-rc1+.conf`
   has menu id `fedora-6.8.0-rc1+` but is advertised as `fedora-6.8.0-rc1`.

`get_entry_number()` only retries with a trailing `.conf` removed, so a `default` (e.g. `LoaderEntryDefault` or
`LoaderEntryOneShot`, which `bli.c` copies verbatim) set to an advertised id such as `fedora-6.8.0` or
`fedora-6.8.0-rc1` matches no menu entry and entry 0 boots. The BLI page describes identifiers as the file name
with the `.conf`/`.efi` suffix removed, which is what `LoaderEntries` follows; plain and numeric-counter BLS
entries are consistent, the two cases above are not.

Not a straightforward fix. The robust approach is one helper computing the canonical id (strip `.conf`/`.efi`,
strip `+N[-M]` only when numeric) and using it in `bls_create_entry()`, `uki_create_entry()` and both loops of
`set_bli_loader_entries()`. That changes the menu id of UKI entries (today `foo.efi`), so the author must decide
whether `get_entry_number()` keeps accepting the old form for existing `default=foo.efi` configurations.

### Issue 6: `LoaderEntries` is overwritten, not accumulated, by repeated calls of the same command (blsuki.c)

**Location:** `grub-core/commands/blsuki.c`, `blsuki_cmd()` line 1772, `set_bli_loader_entries()` lines 1542-1563
(commit 1)

`blsuki_cmd()` rebuilds `entries` from scratch on every call (line 1772) and `set_bli_loader_entries()` lists
only the entries whose `visible` flag that call set. The previous value is merged only when the other command's
flag is "1" (`blscfg` reads `blsuki_entries_uki`, `uki` reads `blsuki_entries_bls`, lines 1547-1549). So
`blscfg --show-default` followed by `blscfg --show-non-default` (both documented as filters, `grub.texi` 7245-7270)
leaves `LoaderEntries` holding only the non-default entries: the default entry, which is in the menu, is no longer
advertised. `blscfg -e A` followed by `blscfg -e B` ends with only B. The BLI page says the variable tells the OS
which entries the loader discovered, in on-screen order.

Not a straightforward fix. Also merging when the command's own flag is set would work only if previous and new
ids are comparable: the merge compares the stored id with `entry->filename` (line 1641), which can still carry
the counter or, for UKI, the extension, so duplicates from re-running the same filter would be missed (or, for
plain names, rejected as "duplicate file"). It depends on the canonical-id helper from Issue 5.
