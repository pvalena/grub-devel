## Re-review

Commits 1-5, 7-8 and 11 (new hashes 8a8609e2c, 2b4bcdcfc, b79d8e5df, da300dc6c, b7e36b407,
d6201cee3, ea4b3364d, 02a3844d6) are patch-identical to the matching commits from the previous
round -- the only diff is the `index aaa..bbb` blob line, which shifts because new commit 6
touches the same file earlier in the series and because `origin/master` was rebased forward
underneath the whole branch. Commit 10 (`Enumerate once`, 73d1607ad) is reworked, but only in a
code comment and the commit message: both now additionally say a device that *disappears*
mid-session "stays listed, and opening it fails" -- this documents previous Issue 2 but makes no
functional change (`grub_obdisk_iterate()` still runs `if (disks_enumerated == 0)
enumerate_devices ();` at line 1261). Commit 6 (af7006eb5) is new.

**Previous Issue 1 is fixed.** New commit 6 (af7006eb5, "Release a device after an I/O error")
replaces `dev->opened = 0;` with `close_disk (dev);` at exactly the three sites flagged
(`obdisk_prepare()` ~line 745, `grub_obdisk_read()` ~line 771, `grub_obdisk_write()` ~line 799),
matching the previously drafted fix verbatim:

```diff
-      dev->opened = 0;
+      close_disk (dev);
```

Traced the chain at the new tip: `close_disk()` (line 89) now runs on every error path, so it
calls `grub_ieee1275_close (dev->ihandle)`, zeroes `dev->ihandle`/`dev->opened`/`dev->dirty`, and
invalidates the block cache before the error returns. The next `ensure_open()` call then sees
`dev->opened == 0` with the firmware instance genuinely closed, so `close_controller_users (...,
keep_disk = dev, ...)` -- which deliberately does not close `dev` itself -- no longer skips a
handle that is still open; there is nothing left open to skip. A retry after a transient I/O
error now opens exactly one instance of the target, restoring the single-instance guarantee
`obdisk_single_instance=1` depends on, and the IEEE1275 instance-handle leak / stale-cache-key
risk on firmware without that limit is gone too. `dev->ihandle` is not read again on any of the
three return paths, so closing it there does not change the returned error or any other logic --
no new issue introduced by the fix.

**Previous Issue 2 is unchanged** -- still open, renumbered below as the sole remaining issue.

## Issues Found

### Issue 1 (previously Issue 2): "Enumerate once" only detects newly-appeared devices, not
removed ones, for ls/search

**Location:** `grub-core/disk/ieee1275/obdisk.c`, `grub_obdisk_iterate()` line ~1245-1262

Commit `73d1607ad` ("Enumerate once") gates `enumerate_devices()` behind `if (disks_enumerated
== 0)`. `enumerate_devices()` is the only code that clears a stale `valid` flag (via
`invalidate_all_disks()` before re-scanning), so after the first `ls`/search-driven iteration in
a session, every later one reuses the same `valid` flags: a device that appears later is missed,
and a device that *disappears* later stays listed as valid for the rest of the session too. Both
cases are now acknowledged in this round's updated comment and commit message, but neither is
fixed. `find_grub_devpath()` (unchanged) still re-enumerates whenever a specific-name lookup
fails, so this only affects the "list everything" path. It fails safely -- opening a stale entry
gets a clean `GRUB_ERR_UNKNOWN_DEVICE` -- so this is a listing-accuracy gap, not a crash or
corruption.

Not a straightforward fix. The commit message shows the author already tried the natural
alternative (re-enumerating on `GRUB_DISK_PULL_RESCAN`) and reverted it because every consumer of
the device list ends up offering each pull level in turn, reintroducing the "minutes per search"
cost this series exists to eliminate. A cheaper staleness signal that also catches removal isn't
present in this series; that trade-off is for the author to make.

For more details, see
[pr255_reasoning.txt](https://gitlab.freedesktop.org/pvalena/grub/-/blob/main/reviews/pr255_reasoning.txt)
-- Issue 1 there is the now-fixed stale-ihandle bug (see Re-review above); Issue 2 there is the
issue above.
