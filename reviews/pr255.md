# AI Review: MR !255 - obdisk: sparc64 single-instance workaround, write support, leak fixes

10 commits to the sparc64 IEEE1275 `obdisk` driver: several resource-leak and NULL-deref fixes,
an "open on demand" refactor, `disk_write` support (needed for `save_env`/`grub-reboot` on
sparc64), a flush-on-close for written devices, and an opt-in workaround
(`obdisk_single_instance`) for firmware that faults when more than one instance is open per disk
controller. One generic `grub-core/lib/disk.c` hardening commit is included alongside the driver
changes.

**Commits:**
1. **262daf49a** - disk: Fail cleanly when a disk driver has no write method
2. **415c08794** - disk/ieee1275/obdisk: Close the parent ihandle on an early failure
3. **6a12c93b8** - disk/ieee1275/obdisk: Open a device on demand
4. **d26fae2a5** - disk/ieee1275/obdisk: Add write support
5. **ed5b331bd** - disk/ieee1275/obdisk: Flush a written device when it is closed
6. **eb4fc7383** - disk/ieee1275/obdisk: Free the scan buffer in scan_sparc_sas_2cell()
7. **292511240** - disk/ieee1275/obdisk: Free the encoded unit address in canonicalise_disk()
8. **f7e1eb4a2** - disk/ieee1275/obdisk: Do not look up a NULL canonical name
9. **7f86f7219** - disk/ieee1275/obdisk: Enumerate once
10. **5931f8467** - disk/ieee1275/obdisk: Keep one open instance per controller when asked

Commit messages accurately describe the changes. Commits 1, 2, 6, 7, and 8 are independent,
narrow fixes, each confirmed against the actual source (not just the diff): commit 2's leak is a
local `ihandle` distinct from `op->ihandle`; commit 6/7's frees match the already-correct sibling
function; commit 8's NULL-deref is real (`grub_strcmp()` dereferences its second argument as soon
as the first is non-empty, and `grub_named_list_find()` is reachable with `canon == NULL` once
`disk_devs` is non-empty). Commits 3-5 and 9-10 build the "open on demand" / single-instance
machinery; see Issue 1 for a gap in how the two interact.

## Issues Found

### Issue 1: I/O-error paths leave a stale, unclosed ihandle that the single-instance logic
assumes is already closed

**Location:** `grub-core/disk/ieee1275/obdisk.c`, `obdisk_prepare()` line ~745,
`grub_obdisk_read()` line ~770, `grub_obdisk_write()` line ~798, interacting with
`ensure_open()` line ~684-691

On a seek/read/write error, all three sites do only `dev->opened = 0;` and return an error --
`dev->ihandle` is left at its old, still-open value; nothing calls `grub_ieee1275_close()` or
invalidates the block cache. Commit ed5b331bd added `close_disk()` specifically to do this
correctly (close the ihandle, zero it, clear `dirty`, invalidate the cache), but none of the
three error sites use it:

```c
  grub_ieee1275_seek (dev->ihandle, pos, &result);
  if (result < 0)
    {
      dev->opened = 0;
      return grub_error (GRUB_ERR_READ_ERROR, "seek error, can't seek block %llu", ...);
    }
```

`ensure_open()` treats `dev->opened == 0` as "safe to reopen without closing anything of `dev`'s
own":

```c
  if (dev->opened != 0)
    return GRUB_ERR_NONE;

  close_controller_users (dev->name, controller_len (dev->name), dev, NULL);
  ...
  dev->ihandle = ihandle;
  dev->opened = 1;
```

`close_controller_users()` is called with `keep_disk = dev`, i.e. it deliberately does not touch
`dev`'s own handle, only siblings on the same controller -- correct when `opened == 0` really
means "closed via `close_disk()`", wrong when it means "errored but still open". So: disk A hits
a transient seek/read/write error (`dev->opened = 0`, `dev->ihandle` still `H1`, still open in
firmware); the next access to A calls `ensure_open()`, which opens a *second* instance `H2` on
the same target while `H1` is still open, then overwrites `dev->ihandle` with `H2` -- `H1` is
never closed. On firmware without the single-instance limit this is a permanent per-error
IEEE1275 instance-handle leak (plus a latent block-cache-key-reuse risk, the exact hazard
ed5b331bd's cache invalidation exists to prevent). On the firmware this MR specifically targets
(`obdisk_single_instance=1`), it transiently puts two open instances on one controller for the
very target the workaround exists to protect -- i.e. it can reproduce the "Fast Data Access MMU
Miss" fault this series exists to fix, via a plain I/O retry rather than the two-different-disks
scenario the series was tested against.

**Draft fix** -- use the existing `close_disk()` helper instead of the bare flag reset (safe at
all three sites: `dev->opened` is known non-zero there, matching `close_disk()`'s own guard, and
`dev->ihandle` is not used again on any of these return paths):

```diff
--- a/grub-core/disk/ieee1275/obdisk.c
+++ b/grub-core/disk/ieee1275/obdisk.c
@@ obdisk_prepare()
   if (result < 0)
     {
-      dev->opened = 0;
+      close_disk (dev);
       return grub_error (GRUB_ERR_READ_ERROR, "seek error, can't seek block %llu",
                          (long long) sector);
     }
@@ grub_obdisk_read()
   if (result != (grub_ssize_t) (size << disk->log_sector_size))
     {
-      dev->opened = 0;
+      close_disk (dev);
       return grub_error (GRUB_ERR_READ_ERROR, N_("failure reading sector 0x%llx "
                                                  "from `%s'"),
                          (unsigned long long) sector,
                          disk->name);
     }
@@ grub_obdisk_write()
   if (result != (grub_ssize_t) (size << disk->log_sector_size))
     {
-      dev->opened = 0;
+      close_disk (dev);
       return grub_error (GRUB_ERR_WRITE_ERROR, N_("failure writing sector 0x%llx "
                                                   "to `%s'"),
                          (unsigned long long) sector,
                          disk->name);
     }
```

### Issue 2: "Enumerate once" only detects newly-appeared devices, not removed ones, for
ls/search

**Location:** `grub-core/disk/ieee1275/obdisk.c`, `grub_obdisk_iterate()` line ~1245-1262

Commit 7f86f7219 gates `enumerate_devices()` behind `if (disks_enumerated == 0)`.
`enumerate_devices()` is the only code that clears a stale `valid` flag (via
`invalidate_all_disks()` before re-scanning), so after the first `ls`/search-driven iteration in
a session, every later one reuses the same `valid` flags: a device that appears later is missed
(acknowledged in the commit message), but a device that *disappears* later stays listed as valid
for the rest of the session too (not mentioned). `find_grub_devpath()` (unchanged) still
re-enumerates whenever a specific-name lookup fails, so this only affects the "list everything"
path. It fails safely -- opening a stale entry gets a clean `GRUB_ERR_UNKNOWN_DEVICE` -- so this
is a listing-accuracy gap, not a crash or corruption.

Not a straightforward fix. The commit message shows the author already tried the natural
alternative (re-enumerating on `GRUB_DISK_PULL_RESCAN`) and reverted it because every consumer of
the device list ends up offering each pull level in turn, reintroducing the "minutes per search"
cost this series exists to eliminate. A cheaper staleness signal that also catches removal isn't
present in this series; that trade-off is for the author to make.

For more details, see
[pr255_reasoning.txt](https://gitlab.freedesktop.org/pvalena/grub/-/blob/main/reviews/pr255_reasoning.txt).
