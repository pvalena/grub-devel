# AI Review: MR !247 - Make efi machines load an env block from a variable

1 commit that adds `grub_efi_env_init()` to `kern/efi/init.c`: it reads the EFI variable `GRUB_ENV`, applies each
entry with `grub_envblk_iterate()` and `grub_env_set()` before `grub_efidisk_init()`, and builds `lib/envblk.c` into
the EFI kernel.

**Commits:**
1. **602db925a** - Make efi machines load an env block from a variable

## Issues Found

### Issue 1: Security-relevant: unauthenticated `GRUB_ENV` variable can preset `check_signatures=no`

**Location:** `grub-core/kern/efi/init.c`, `set_var()` and `grub_efi_env_init()`, lines 106-128 (called at line 159)

```c
static int
set_var (const char *name, const char *value, void *whitelist __attribute__((__unused__)))
{
  grub_env_set (name, value);          /* every entry, no filtering */
  return 0;
}
...
  grub_efi_get_variable ("GRUB_ENV", &efi_grub_guid, &envblk_s.size, (void **) &envblk_s.buf);
  ...
  grub_envblk_iterate (envblk, NULL, set_var);   /* NULL: no whitelist */
```

`grub_efi_env_init()` runs in `grub_efi_init()` after `grub_lockdown()` (lines 151-155) and before any embedded module's
`GRUB_MOD_INIT`. `loadenv`'s `set_var` supports a whitelist (the docs warn that omitting it can set
`check_signatures=no`, `docs/grub.texi` lines 8113-8123); this one supplies none, reads the variable with
`attributes == NULL` (`efi.c:287-290`), and has no lockdown check. `GRUB_MOD_INIT(pgp)` reads
`grub_env_get ("check_signatures")` (`pgp.c:978-982`), and its implicit `enforce` default is applied only `if (!val)`
(`pgp.c:1011-1012`), so a preset value wins; with `sec == 0` `grub_pubkey_init()` returns `SKIP_VERIFICATION`
(`pgp.c:898-902`).

Concrete failing input: the variable contains `# GRUB Environment Block\ncheck_signatures=no\n`. On the next boot, in a
`core.img` that carries `--pubkey` and relies on the implicit default (`docs/grub.texi` lines 10003-10008), pgp stops
enforcing, so an unsigned `grub.cfg`, modules, kernel, initrd and grubenv are accepted. Editing `grub.cfg` alone cannot
do that there, since it needs a valid `.sig`. Under Secure Boot, kernels and modules still fail closed unless shim_lock
authenticates them (`lockdown.c:34-55`, `verifiers.c:152-171`), but an unsigned config could then inject kernel
command-line arguments for a shim-authenticated kernel; I did not confirm that pgp plus shim_lock occurs in practice.
The attacker must be able to write the variable. No writer exists in-tree, so who can, and with which attributes, is not
verifiable here; if it is runtime-accessible, or with physical access, the precondition is met.

Precedent: `sb.c:99-110` honours `MokSBState` only without `RUNTIME_ACCESS`, and `appendedsig.c:1206, 1247` refuse
changes under lockdown. Not affected: `check_appended_signatures`, `appendedsig_key_mgmt` (read hooks ignore the stored
value), `lockdown`/`shim_lock` (never read), `prefix`/`root`/`cmdpath` (overridden later), `tpm_fail_fatal` (default
false, so a preset can only tighten it).

Not a straightforward fix; the author must choose:
- (a) skip or reject the variable when `RUNTIME_ACCESS` is set, as `sb.c` does;
  `grub_efi_get_variable_with_attributes()` already exists (`efi.c:214`, `efi.h:90`).
- (b) pass a whitelist of harmless variable names as `hook_data` (the `whitelist` parameter is already there, as in
  `loadenv.c`); recommended, possibly together with (a).
- (c) skip the variable when `grub_is_lockdown ()`; this protects Secure Boot boots only, not a non-SB `--pubkey` setup.
- (d) verify a signature over the block first; no verifier is available that early (`grub_verifiers_init()` runs later).

## Additional findings

Secondary: the 25-byte `# GRUB Environment Block` signature is skipped unchecked (`grub_envblk_open()` is bypassed),
so a variable without it is parsed from offset 25. The `grub_efi_get_variable()` status is ignored (stale `grub_errno`
only after an OOM). Bounds and `grub_malloc`/`grub_free` pairing of the exact-size buffer were traced and are fine.
The variable name, GUID and format are not documented in-tree. `envblk.c` now exists in both the EFI kernel and
`loadenv.mod`, with no duplicate-symbol clash (its header has no `EXPORT_FUNC`).
