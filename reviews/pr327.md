## Issues Found

### Issue 1: Security-relevant: RAID10 chunk with nstripes 0 or 1 still reads stripe[1] past the validated item

**Location:** `grub-core/fs/btrfs.c`, `grub_btrfs_read_logical()` (RAID10 case ~1120-1150, check ~1287-1291, retry
loop ~1315-1323) and `btrfs_read_from_chunk()` (~709)

Commit 5 bounds the stripe array using the effective `nstripes` (line 1035: raw 0 becomes 1), so a one-stripe item
needs only 32 + 48 = 80 bytes and passes. For RAID10, `nstripes / nsubstripes ? : 1` is `1/2 -> 1`, so `stripen`
is 0, and `redundancy = nsubstripes = 2` (the only `nsubstripes` check is `!= 2`, which a crafted 2 passes). The
retry loop then calls `btrfs_read_from_chunk()` with `i == 1`, which does `stripe += stripen + redundancy` and
reads `stripe[1]`, bytes 80..112 of the 80-byte item.

Failing input: a crafted btrfs filesystem with a RAID10 chunk, `nstripes` 0 or 1, `nsubstripes` 2, and a
`stripe[0].device_id` that names no attached device. `find_device()` then returns NULL, the i == 0 read returns
`GRUB_ERR_READ_ERROR`, and the loop retries with `i == 1`; no real disk failure is needed. The 16 bytes read
(`device_id`, `offset`) are 16 bytes of heap for a chunk-tree item, or neighbouring superblock/`grub_btrfs_data`
members for a bootstrap entry. They feed `find_device()` and the disk-read offset; no path returns them to the
attacker. Precondition: on-disk data GRUB reads. Other profiles have no exempt case (traced in the reasoning file).

**Draft fix** -- reject too few stripes for RAID10 so the geometry is consistent with `nsubstripes`:

```diff
--- a/grub-core/fs/btrfs.c
+++ b/grub-core/fs/btrfs.c
@@ case GRUB_BTRFS_CHUNK_TYPE_RAID10:
-	      if (grub_le_to_cpu16 (chunk->nsubstripes) != 2)
+	      if (grub_le_to_cpu16 (chunk->nsubstripes) != 2
+		  || grub_le_to_cpu16 (chunk->nstripes) < 2)
 		{
```

(The error message there would then also name `nstripes`; the alternative is a separate check with
`GRUB_ERR_BAD_FS` and `goto out`.) Valid RAID10 items have `nstripes >= nsubstripes == 2`.
