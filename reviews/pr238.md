# AI Review: MR !238 - CI: create a 'Release' pipeline

1 commit adding a tag-triggered release pipeline: build artifacts (multi-target windowszip +
`make dist` tarballs), GPG-sign them, upload to the generic package registry, and create a
GitLab release. New scripts under `.gitlab-ci/script/` plus `release.yml` /
`release-artifacts.yml` wiring and a base image bump.

**Commits:**
1. **f707e479b** - CI: Create a 'Release' Pipeline

## Issues Found

### Issue 1: `set -x` leaks the GPG private key, passphrase, and job token into CI logs

**Location:** `.gitlab-ci/script/sign-artifacts.sh` (lines 3, 6, 12-14);
`.gitlab-ci/script/upload-artifacts.sh` (lines 3, 12, 19)

`sign-artifacts.sh` runs with `set -xeu -o pipefail`. With xtrace (`-x`) on, bash prints every
command with its variables expanded, so these lines echo secrets into the job log:

```bash
echo "$GPG_PRIVATE_KEY" | base64 -d | gpg --batch --import -                       # line 6
gpg ... --passphrase "$GPG_PASSPHRASE" --detach-sign $GRUB_CI_COMMIT_TAG.tar.gz    # lines 12-14
```

The trace `+ echo <base64 signing key>` and `+ gpg ... --passphrase <passphrase> ...` expose
the release signing key material and its passphrase. `upload-artifacts.sh` similarly traces
`curl --header "JOB-TOKEN: $CI_JOB_TOKEN"`, printing the job token. GitLab only masks variables
explicitly configured as *masked*, and only when they meet its masking constraints (single
line, limited charset) — a passphrase often will not qualify — so this must not be relied on.
Leaking the long-lived GPG signing key would let anyone with log access forge signed GRUB
releases.

**Draft fix** -- do not xtrace the secret-handling scripts (drop `-x`):

```diff
--- a/.gitlab-ci/script/sign-artifacts.sh
+++ b/.gitlab-ci/script/sign-artifacts.sh
-set -xeu -o pipefail
+set -eu -o pipefail
```

```diff
--- a/.gitlab-ci/script/upload-artifacts.sh
+++ b/.gitlab-ci/script/upload-artifacts.sh
-set -xeu -o pipefail
+set -eu -o pipefail
```

If tracing is wanted elsewhere in these scripts, bracket only the secret commands with
`set +x` … `set -x` instead. Passing the passphrase via `--passphrase-fd` / a file rather than
on the `gpg` command line would further avoid argv exposure.

### Issue 2: `create-release.sh` uses bash-only syntax under `#!/bin/sh`

**Location:** `.gitlab-ci/script/create-release.sh` (line 1 shebang; line 3 `pipefail`; line 45
`[[ =~ ]]`)

The script declares `#!/bin/sh` but uses two bash-only constructs:

```sh
set -xeu -o pipefail                       # line 3: -o pipefail is not POSIX
...
if [[ "$CI_COMMIT_TAG" =~ $RC ]]; then     # line 45: [[ ]] and =~ are bash-only
```

This job runs in `registry.gitlab.com/gitlab-org/release-cli:latest`, whose `/bin/sh` is
almost certainly not bash (dash/busybox `ash`). Under dash, `set -o pipefail` fails at line 3;
under busybox `ash`, `[[` is unknown at line 45. Either way the script aborts (`set -e`), so
the release is never created — or, at best, the RC-detection branch silently misbehaves. The
sibling scripts correctly use `#!/bin/bash` for their bash-isms; this one is the outlier.

**Draft fix** -- make it POSIX (the release-cli image may not ship bash):

```diff
--- a/.gitlab-ci/script/create-release.sh
+++ b/.gitlab-ci/script/create-release.sh
-set -xeu -o pipefail
+set -xeu
```

```diff
-if [[ "$CI_COMMIT_TAG" =~ $RC ]]; then
+if echo "$CI_COMMIT_TAG" | grep -q "$RC"; then
```

(Alternatively switch the shebang to `#!/bin/bash` *if* that image is confirmed to ship bash;
POSIX is the safer choice. `-x` here is fine — this script handles no secrets.)
