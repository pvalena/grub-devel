# AI Review: MR !227 - grub-protect: TPM2 authorized policy support

7 commits adding a TPM2 authorized-policy workflow to `grub-protect`: two new actions
(`generate-authkey`, `sign-policy`), the `--tpm2-authkey` option, the TSS2 plumbing to sign a
policy digest (`grub_tpm2_sign`, `TPMT_SIG_SCHEME`/`TPMT_TK_HASHCHECK` marshallers), an NV-index
re-define path, docs, and an emu test. This lets a PCR policy be wrapped in `TPM2_PolicyAuthorize`
so the sealed key can be re-authorized for new PCR values by re-signing, without re-sealing.

## Additional findings

- The `TPM2_VerifySignature` marshalling fix (692310f14) has **no runtime effect** for the sole
  in-tree caller (`tpm2_key_protector/module.c:726`, which passes `authCommand == NULL`): with a
  NULL auth area, `keyHandle` is the only field packed either way. It is a correct spec-conformance
  fix for future callers, and the commit message says exactly that.
- `grub_tpm2_sign` and the new `TPMT_SIG_SCHEME`/`TPMT_TK_HASHCHECK` marshallers pack fields in the
  TPM2 wire order (handle → auth area → params); the sign / policy-authorize / re-sign data flow is
  consistent (sign the *pre*-authorize policy digest, hashed via `TPM2_Hash` before `TPM2_Sign`).
- One spec deviation in the generic `TPMU_ASYM_SCHEME` (un)marshaller, unreachable with current
  callers: it now packs a `hashAlg` for `TPM_ALG_RSAES` (whose union member is empty in the TPM 2.0
  structure tables). No in-tree path marshals an RSAES scheme, so there is no concrete impact.
- Memory/handle cleanup in every new host-side function was traced (auth-key buffers, ASN.1
  structures, DER buffers, loaded key/session/SRK handles) — freed/flushed on all paths, no leak or
  use-after-free.
