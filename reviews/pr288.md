# AI Review: MR !288 - disk/luks2: Validate indices before shifting 64-bit masks

1 commit fixes shift-count undefined behavior in LUKS2 JSON parsing: segment/keyslot indices
read from the on-disk JSON metadata were used directly as shift counts against the `int` literal
`1` with no range check, so an index of 32 or more is UB (shift count exceeding the promoted left
operand's width), and even for in-range high bits the result was truncated to 32 bits before
being stored into the 64-bit `segments`/`keyslots` bitfields.

## Additional findings

`out->segments`/`out->keyslots` and `grub_luks2_keyslot_t.idx` / `grub_luks2_segment_t.idx` are
all `grub_uint64_t` (`grub-core/disk/luks2.c`, `grub_luks2_digest_t`/`grub_luks2_keyslot_t`/
`grub_luks2_segment_t`), so `sizeof (out->segments) * 8` / `sizeof (d->keyslots) * 8` correctly
evaluate to 64 on every platform. Each of the four sites that previously did `1 << bit` now
bounds-checks the index against that 64-bit width *before* the shift (`luks2_parse_digest`'s two
loops, and the `k->idx`/`s->idx` checks newly added in `luks2_get_keyslot`), and the shift itself
now widens the literal to `((grub_uint64_t) 1) << bit`, so no shift can reach UB or lose bits
post-fix. `bit`/`k->idx`/`s->idx` are read via `grub_json_getuint64()`, which only writes its
out-parameter on success (`grub-core/lib/json/json.c`), and each new bounds check is placed as
the last term of a short-circuited `||`/`if`, so it only evaluates once the value is known good.
This matches the shift-UB bug class already seen in this repo's reviews (pr165).
