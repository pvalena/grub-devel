# AI Review: MR !278 - efibootnext: fix misbehaviour on efivar>=39 and MBR ESP

1 commit fixes `util/grub.d/31_efi_bootnext.in` for two efibootmgr/efivar quirks: efivar >= 39
drops the `File(...)` decoration from device paths (breaking the existing `sed` extraction and
shim-chainload detection), and the self-entry filter only recognised GPT PARTUUIDs, so an ESP
on an MBR disk was never matched and the running GRUB could offer itself as a BootNext target.
Adds `tests/grub_mkconfig_bootnext_path_test.in` and expands
`tests/grub_mkconfig_bootnext_self_test.in`; registers the new test in `Makefile.util.def`.

**Commits:**
1. **8404f2283** - efibootnext: fix misbehaviour on efivar>=39 and MBR ESP

## Re-review

This commit was reworked/force-pushed (previously 23024bd80, 320/57; now 8404f2283, 333/57,
still 1 commit). The prior round reported ISSUES(1): the bare-path shim-detection `case` ran
before the script's lowercase normalisation, so a shim path with non-canonical case (e.g.
`\efi\otheros\shimx64.efi`) skipped the UTF-16LE chainload-target decode, letting a firmware
updater's entry slip past the os-prober filter. Full prior trace in `pr278_reasoning.txt`.

The old commit hash still resolves (`git cat-file -t 23024bd80` -> `commit`), so the two
rounds' patch content were diffed directly. Aside from 5 unrelated master commits in between
(none touching these files), exactly two things changed, and both are the fix:

```diff
-        case "${efi_file}" in
-            '\EFI\'*'\shim'*.efi)
+        case "`printf '%s' "${efi_file}" | tr 'A-Z' 'a-z'`" in
+            '\efi\'*'\shim'*.efi)
                 if printf '%s\n' "${optdata}" | grep -q '^\([2-7][0-9a-f]00\)\+0000$'; then
```

plus a new regression test in `tests/grub_mkconfig_bootnext_path_test.in`: the single hardcoded
shim path in the Boot0010/Boot0012 sub-test became a loop over five case variants (`\EFI\...`,
`\efi\...`, `\EfI\OtherOS\...`, `\EFI\...\SHIMX64.efi`, `\EFI\...\shimx64.EFI`), for both the
decorated and bare efibootmgr formats.

The fix is exactly the draft proposed in round 1 (lowercase the match subject and pattern, same
idiom as the file's two other identity checks), and it is correct: it was traced against the
same scenario round 1 documented, and lowercasing the subject makes all five case variants match
while the decoded-target assignment inside the branch is unaffected (independent of case). No
other code in the file, in `tests/grub_mkconfig_bootnext_self_test.in`, or in `Makefile.util.def`
differs from round 1's already-reviewed content.

The new and expanded tests were run directly against the pr278 script (copied out, with only the
`/sys/firmware/efi` reachability guards bypassed in the disposable copy); both pass. To confirm
the new shim-case loop is a real regression test, the fix was additionally reverted in the
disposable copy only and `path_test.sh` was re-run: it fails exactly as predicted ("updater
matched first loader" for the lowercase-`\efi\` case), confirming both that the fix is effective
and that the added test actually exercises it.
