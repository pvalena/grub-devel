# AI Review: MR !278 - efibootnext: fix misbehaviour on efivar>=39 and MBR ESP

1 commit fixes `util/grub.d/31_efi_bootnext.in` for two efibootmgr/efivar quirks: efivar >= 39
drops the `File(...)` decoration from device paths (breaking the existing `sed` extraction and
shim-chainload detection), and the self-entry filter only recognised GPT PARTUUIDs, so an ESP
on an MBR disk was never matched and the running GRUB could offer itself as a BootNext target.
Adds `tests/grub_mkconfig_bootnext_path_test.in` and expands
`tests/grub_mkconfig_bootnext_self_test.in`; registers the new test in `Makefile.util.def`.

Both the new and the expanded test file were run directly against the exact pr278 script
(copied out, with only the `/sys/firmware/efi` reachability guards bypassed in the disposable
copy) and passed; the two headline fixes (bare-path `File()` extraction, MBR PARTUUID
self-match) are correct. A narrower gap in a third feature added by the same commit -- the
shim UTF-16LE chainload-target decode -- is below.

**Commits:**
1. **23024bd80** - efibootnext: fix misbehaviour on efivar>=39 and MBR ESP

## Issues Found

### Issue 1: shim-path detection is case-sensitive, unlike every other identity check here

**Location:** `util/grub.d/31_efi_bootnext.in`, main loop, lines ~217-231

In the bare-path (efivar>=39, no `File()` decoration) branch, the shim-detection `case` runs
*before* the script's own lowercase normalisation:

```sh
        case "${efi_file}" in
            '\EFI\'*'\shim'*.efi)
                if printf '%s\n' "${optdata}" | grep -q '^\([2-7][0-9a-f]00\)\+0000$'; then
                    ...
                    efi_file=".`printf '%b' "${opt_suffix}"`"
                fi ;;
        esac
    fi
    ...
    efi_file="`printf '%s' "${efi_file}" | \
        tr '\134A-Z' '/a-z'`"
```

`SELF_VENDORS`, `osp_efi`, and `entry_vendor` are all compared in lowercase (each is built or
read after a `tr 'A-Z' 'a-z'`), but this `case` compares `${efi_file}` in whatever case the
firmware/devpath used, before the unconditional `tr` two lines later. A path like
`\efi\otheros\shimx64.efi` (FAT is case-insensitive, so this is a perfectly valid on-disk
name -- firmware, OEM entries, or non-canonical install tooling can write it this way) fails
to match `'\EFI\'*'\shim'*.efi'` outright, so the UTF-16LE optional-data decode never fires.
`efi_file` then stays at the shim's own path; if os-prober recognises that path as an OS loader
(the expected, common case, since shim is the real first-stage loader os-prober reports),
the entry is kept in the BootNext menu -- even though its optional data actually chainloads to
something else (e.g. a firmware updater's `fwupdx64.efi`). That is precisely the failure mode
this commit's shim-decode feature was added to prevent, for entries whose directory case
happens to differ from canonical uppercase `\EFI\`.

`grub-install` and mainstream shim-signed packaging both hardcode `\EFI\...` uppercase, so
canonical installs are unaffected -- this is a narrow gap (non-canonical/third-party install
tooling or OEM/firmware-written entries), not a self-reboot-loop risk, and the MR's two
headline fixes remain correct.

**Draft fix** -- lowercase the match subject, consistent with the two other identity checks in
this file:

```diff
--- a/util/grub.d/31_efi_bootnext.in
+++ b/util/grub.d/31_efi_bootnext.in
@@
-        case "${efi_file}" in
-            '\EFI\'*'\shim'*.efi)
+        case "`printf '%s' "${efi_file}" | tr 'A-Z' 'a-z'`" in
+            '\efi\'*'\shim'*.efi)
                 if printf '%s\n' "${optdata}" | grep -q '^\([2-7][0-9a-f]00\)\+0000$'; then
```

Only the case-comparison target changes (`tr 'A-Z' 'a-z'`, not the `tr '\134A-Z' '/a-z'` form
used later, since the pattern still relies on literal backslashes). The later unconditional
`tr` already lowercases `efi_file` a second time regardless of which branch ran, so this is
idempotent for every other path through this block.
