## Issues Found

### Issue 1: `fuzzdev` has `size >> 9` sectors, so GRUB rejects reads past the input and zero-fill never runs

**Location:** `fuzz/grub_fuzzing_platform.c`, `fuzz_disk_open()` (line 120) and `fuzz_disk_read_cb()`
(lines 141-166, comment at 137-139), commit 5afa7bac1. The claim is repeated in that commit message and in
`docs/grub-dev.texi` (commit e0ebb339d, "Writing a new fuzzer", the `fuzz_disk_set_image` entry).

The commit message says the device "zero-fills reads past the end of the input, which lets a parser be driven
from an arbitrarily short input"; the manual says reads past the end "are zero-filled, so a parser can be
driven from a short input"; the comment above `fuzz_disk_read_cb()` says the region past the end "is
zero-filled, which is safe". But `fuzz_disk_open()` publishes `disk->total_sectors = image_size >> 9`, and
every read goes through `grub_disk_read()`, which calls `grub_disk_adjust_range()` first (`grub-core/kern/disk.c:533`,
`grub-core/kern/disk_common.c:44-48`). That returns `GRUB_ERR_OUT_OF_RANGE` ("attempt to read or write
outside of disk `fuzzdev'") for any request that is not entirely inside `total_sectors`, before the device
callback is reached. The cache-fill path adds its own `sector + 64 < total_sectors` guard (`disk.c:453-455`),
and the other two `disk_read` call sites (`disk.c:494`, `disk.c:606`) are sized from the already-checked
request. So the callback only ever sees ranges fully inside the input, and its `byte_offset >= data_len` and
`avail < bytes` branches cannot run.

Effects:
- A truncated image (e.g. a 3000-byte input = 5 sectors) gets `GRUB_ERR_OUT_OF_RANGE` on the first read past
  sector 5 instead of zeros; inside `grub_ext2_mount()` that is turned into "not an ext2 filesystem"
  (`ext2.c`, `fail:` label), so the parse stops there rather than continuing on zero-filled metadata.
- The last `size % 512` bytes of every input (all of it when `size < 512`) can never be read, because the
  division floors; mutations there cannot influence the parser.
- Authors of future targets are told short inputs work through zero-fill, which they do not.

Not a straightforward fix: the author has to choose between (a) presenting a capacity larger than any input so
GRUB's range check passes and the existing zero-fill is actually used, or (b) dropping the zero-fill claim from
the commit message, comment and manual (and the dead branches). One sketch of (a):

```diff
--- a/fuzz/grub_fuzzing_platform.c
+++ b/fuzz/grub_fuzzing_platform.c
@@ fuzz_disk_open
-  disk->total_sectors = fuzz_disk_logical_size () >> GRUB_DISK_SECTOR_BITS;
+  /* A fixed capacity well above any input: GRUB's range check then passes and
+     fuzz_disk_read_cb() zero-fills whatever lies past the data.  */
+  disk->total_sectors = GRUB_DISK_KiB_TO_SECTORS (1024 * 1024);	/* 1 GiB */
@@ (above the "fuzzdev" disk device callbacks)
-/* Logical capacity presented to GRUB. */
-static grub_size_t
-fuzz_disk_logical_size (void)
-{
-  return fuzz_image_size;
-}
-
```

`fuzz_disk_logical_size()` is `static` and `fuzz_disk_open()` is its only caller, so the sketch must delete (or
repurpose) it as well: left in place it triggers `-Wunused-function` (in `WARN_FLAGS`, `configure.ac:541`), and
`-Werror` is on by default (`configure.ac:2586-2588`), so the platform file would stop compiling.

Caveats for (a): it changes what the ext2 driver can reach (it may now follow block numbers into zero-filled
space, which can cost time per input), and the capacity must stay small enough that `sector << 9` fits in
`grub_size_t` in the callback.

### Issue 2: `fuzz-get-corpus` leaves its temporary clone behind on any failure

**Location:** `Makefile.fuzz.am`, `fuzz-get-corpus` recipe (lines 117-127), commit eb9881694

The recipe runs `set -e`, creates `tmpdir=\`mktemp -d\``, then `git clone`, `sparse-checkout`, `checkout`,
`mkdir -p fuzz/corpus`, `cp -r`, and only then `rm -rf $$tmpdir`. With `set -e` the shell exits at the first
failing command, so the final `rm -rf` is skipped and nothing else removes the directory. A failure after
`checkout` (`mkdir`/`cp` into `fuzz/corpus/`: read-only tree, no space) therefore leaves the whole fetched
corpus, which the commit message describes as large, in `/tmp`. A failed `git clone` (offline machine,
unreachable mirror, missing branch: the uses the commit message names) is expected to leave at least the empty
`mktemp -d` directory behind for the same reason; that part relies on git's own cleanup behaviour, which is
not readable in this tree.

**Draft fix** -- remove the directory from an `EXIT` trap instead of a trailing command:

```diff
--- a/Makefile.fuzz.am
+++ b/Makefile.fuzz.am
@@ fuzz-get-corpus
 	$(AM_V_GEN)set -e; \
 	tmpdir=`mktemp -d`; \
+	trap 'rm -rf "$$tmpdir"' EXIT; \
 	git clone --depth=1 --filter=blob:none --no-checkout \
 	    -b $(FUZZ_CORPUS_BRANCH) $(FUZZ_CORPUS_REPO) $$tmpdir; \
 	git -C $$tmpdir sparse-checkout set corpus; \
 	git -C $$tmpdir checkout; \
 	mkdir -p fuzz/corpus; \
-	cp -r $$tmpdir/corpus/. fuzz/corpus/; \
-	rm -rf $$tmpdir
+	cp -r $$tmpdir/corpus/. fuzz/corpus/
```

## Additional findings

Spot-checked claims (EMU `grub_malloc` wraps libc `malloc`, the `GRUB_AS_LIST` UBSan note, the `grub_debug_enabled()`
env lookup, the ext2 dictionary constants) match the source. The only build-rule change that reaches non-fuzz builds
is the unconditional `libgnu.a` rule in `Makefile.am` (commit 3, not in its message), a no-op for `make all` as
`SUBDIRS` builds gnulib first. Unverified build impacts: the new manual chapter (`grub-dev.texi` is in
`info_TEXINFOS`, so it builds by default) and the `EXTRA_DIST` additions (`make dist`); no build was run. The env
purge and the `grub_file_verifiers` / `grub_dl_load` stubs look like no-ops at this base.
