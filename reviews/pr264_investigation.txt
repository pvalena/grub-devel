== Motivation check ==

grub_cpu_idle() on i386/x86_64 (include/grub/i386/time.h, include/grub/x86_64/time.h) is a
literal no-op - the `hlt` instruction is commented out with a decades-old "FIXME: this can't
work until we handle interrupts" note. This confirms the commit message's claim: without this
change, grub_getkey()'s idle loop is a genuine 100%-CPU busy spin while waiting at a prompt
(e.g. a LUKS passphrase prompt), on both bare metal and VMs. The fix is solving a real,
verifiable problem, not a placebo.

== Core mechanism: grub_getkey() wait gate (grub-core/kern/term.c) ==

  term = grub_term_inputs;
  if (term && !term->next && !grub_term_poll_usb && term->wait
      && term->wait (term))
    continue;

`grub_term_inputs` is the same list FOR_ACTIVE_TERM_INPUTS iterates (include/grub/term.h:333),
so `term && !term->next` correctly means "exactly one active input terminal" - not an
approximation. If a second terminal is active (e.g. serial + EFI console), or native USB needs
polling (`grub_term_poll_usb` set by grub-core/bus/usb/usb.c when polling starts), the gate is
false and the loop falls through unchanged to `grub_cpu_idle()` - i.e., every path that isn't
"exactly one EFI console, no USB" is byte-for-byte the pre-existing behavior. This scoping
avoids the failure mode of waiting on one terminal's event while input arrives on another,
silently-unpolled terminal.

`struct grub_term_input.wait` is a new field inserted before `void *data`. Every existing
struct grub_term_input instance in the tree uses C99 designated initializers (checked all
~13 instances listed above), so unspecified `.wait` is implicitly NULL - no other terminal
driver needed to be touched, and no positional-initializer struct-layout risk exists.

== grub_console_wait() (grub-core/term/efi/console.c) ==

  if (grub_efi_is_finished || input_wait_failed)
    return 0;
  text_input = term->data;
  if (text_input != NULL)
    events[0] = text_input->wait_for_key;
  else if (grub_efi_system_table->con_in != NULL)
    events[0] = grub_efi_system_table->con_in->wait_for_key;
  else
    return 0;
  if (events[0] == NULL)
    return 0;
  b = grub_efi_system_table->boot_services;
  status = b->create_event (GRUB_EFI_EVT_TIMER, GRUB_EFI_TPL_APPLICATION, NULL, NULL, &events[1]);
  if (status != GRUB_EFI_SUCCESS) { input_wait_failed = 1; return 0; }
  status = b->set_timer (events[1], GRUB_EFI_TIMER_RELATIVE, 20 * 10000);
  if (status == GRUB_EFI_SUCCESS)
    status = b->wait_for_event (ARRAY_SIZE (events), events, &index);
  if (b->close_event (events[1]) != GRUB_EFI_SUCCESS || status != GRUB_EFI_SUCCESS)
    input_wait_failed = 1;
  return status == GRUB_EFI_SUCCESS;

Event lifecycle / leak check: the only event this function owns is events[1] (the timer),
created via create_event. Every path that reaches a successful create_event also reaches
close_event before returning (whether set_timer or wait_for_event subsequently fails) -
traced all 4 exit points: (1) create fails -> return before any event exists to close; (2)
set_timer fails -> status != SUCCESS carries through, close_event still called unconditionally
below; (3) wait_for_event fails -> same; (4) both succeed -> close_event called. No leaked EFI
timer events on any path. events[0] (the firmware-owned wait_for_key event, either from the
ex-interface or con_in) is never created or closed here, correctly - it's not owned by this
function.

20 * 10000 = 200000 (100ns units) = 20ms. Matches the code comment and is independently
confirmed by the test's `grub_test_assert (duration == 200000, NULL)`. GRUB_EFI_EVT_TIMER
(bare, no NOTIFY_SIGNAL, NULL notify function) + boot_services->wait_for_event is an existing
idiom in this tree (grub-core/kern/ia64/efi/init.c uses the identical bare-EVT_TIMER +
create_event pattern), not a novel/unverified construct.

`input_wait_failed` is sticky: once any of create_event/wait_for_event/close_event fails, all
future grub_console_wait() calls short-circuit to 0 (busy-poll fallback) until
grub_efi_console_input_init() runs again (chainload/kexec re-registration), which resets the
flag to 0. This is a conservative but deliberate design - it avoids hammering a firmware whose
event API is already failing, at the cost of not retrying a possibly-transient failure until
reinit. Not a correctness bug; noted as a design trade-off.

Race check (softened in the 2026-10-27 re-review; the original text asserted firmware behaviour
that nothing in this tree shows): whether the firmware's ConIn "wait for key" event stays signaled
while an unread keystroke is queued is firmware behaviour I recall but did not verify from any
source in this tree, and I did not check how EDK2 code uses ConIn->WaitForKey. What the source
does show is that this does not matter for correctness: grub_console_wait() also arms a 20 ms
timer event, so a key that arrives between grub_getkey_noblock()'s failed read and the
wait_for_event call (or a key event that never signals) is picked up by the next poll once the
timer fires (the code comment notes firmware timer granularity may round the 20 ms up).

Reachability of `text_input` path: grub_efi_console_input_init() sets term->data from
grub_efi_open_protocol() for the Simple Text Input Ex protocol; when unavailable it stays NULL
and grub_console_wait() falls back to grub_efi_system_table->con_in->wait_for_key. Both branches
are exercised by the test (check_events(): default con_in path, then the `extended` ex-interface
path via console_input->data = &extended).

== 2. Fresh pass over commit 1 in the resulting tree ==

Wait gate (term.c, grub_getkey): `term = grub_term_inputs; if (term && !term->next && !grub_term_poll_usb && term->wait
&& term->wait (term)) continue;`. grub_term_inputs is the list FOR_ACTIVE_TERM_INPUTS walks (term.h), so "term->next ==
NULL" is exactly "one active input". grub_getkey_noblock() runs before every wait and still calls grub_term_poll_usb,
grub_net_poll_cards_idle and every active getkey, so a wake returning 1 only loops back to the same polling path.

Designated initializers (struct grub_term_input got a new `wait` member before `data`): re-grepped the current tree.
Definitions found: unix/windows emuconsole.c, arc, arm/cros, arm/pl050, at_keyboard, efi, i386/pc, ieee1275, serial,
uboot, usb_keyboard (grub_usb_keyboard_term plus a copied grub_usb_keyboards[16]), xen, tests/fake_input.c, and the two
new tests. All use `.field =` initializers or are zero-initialised arrays, so `.wait` is NULL everywhere except the
EFI and BIOS consoles. No positional initializer exists.

EFI wait (efi/console.c) re-read: events[1] is the only object the function creates; create_event failure returns before
anything exists to close, and every other path calls close_event once. As I recall the UEFI spec, WaitForEvent is only
valid at TPL_APPLICATION (not checked against the spec here); an error return would set input_wait_failed and fall
back to polling, so that case is handled by the same path. `index` is written by firmware but never read: a key wake
and a timer wake are treated alike (both `continue` into a fresh poll), which is why the "timer-only wake" test works.
input_wait_failed is reset in grub_efi_console_input_init() after the grub_efi_is_finished early return.

== 3. Commit 2: x86: Use PAUSE in grub_cpu_idle (include/grub/i386/time.h, include/grub/x86_64/time.h) ==

Both headers had the same blob (4da5ae93c) and get the same new blob (dffa2825e): the empty body becomes
`asm volatile ("pause");` with the FIXME rewritten ("HLT must replace PAUSE below, not just be uncommented alongside

Scope: include/grub/time.h includes <grub/cpu/time.h> only when neither GRUB_MACHINE_EMU nor GRUB_UTIL is defined;
otherwise it supplies its own empty grub_cpu_idle(). So the change cannot reach grub-emu, host utilities or the native

hint instruction that returns after a few cycles cannot change their results; the previous body was empty and the
loops call out-of-line functions, so no compiler-barrier behaviour is lost. PAUSE is the usual x86 spin-wait hint
(general knowledge; I found no in-tree use of it to compare, and did not assemble it: not compiled here).
Commit message claim "PAUSE still spins; it does not replace a blocking wait" is consistent with the code.

== 4. Commit 3: BIOS console wait (term/i386/pc/console.c, int.h, test, CI) ==

grub_console_wait(): regs zero-initialised; eax = 0x8600 (AH=86h), ecx = 0, edx = 20 * 1000 (CX:DX = 20000
microseconds, as in the code comment); flags = GRUB_CPU_INT_FLAGS_DEFAULT | GRUB_CPU_INT_FLAGS_CARRY. In i386-pc
builds GRUB_CPU_INT_FLAGS_DEFAULT is GRUB_CPU_INT_FLAGS_INTERRUPT (int_types.h), so 0x0201 is passed (fits the 16-bit
`flags` member). grub_bios_interrupt (kern/i386/int.S) copies regs->flags to the real-mode `popf` before the `int`
and writes the returned flags back, so `regs.flags & GRUB_CPU_INT_FLAGS_CARRY` after the call is the BIOS's carry.
Presetting CF is conservative: a BIOS that does not clear CF on success is treated as a failed wait (falls back to
polling), never as a successful one. Interrupts are enabled in real mode both by the flags word and by the `sti` at
the end of prot_to_real (realmode.S, GRUB_MACHINE_PCBIOS), i.e. the same conditions every other INT 13h/16h call here
already runs under. The AH=86h semantics (CX:DX microseconds, CF set on error) come from the commit's own comment and
the usual interrupt-list convention; I did not check them against a spec document or real firmware, and the commit
message itself says physical BIOSes were not tested and a hanging firmware call cannot be recovered from.

Failure path: CF set -> input_wait_failed = 1, return 0, so grub_getkey() falls to grub_cpu_idle() (PAUSE from commit 2)
and keeps polling INT 16h; nothing is allocated, so there is nothing to release. The flag is cleared only by the new
`.init` (grub_console_input_init), which grub_term_register_input()/grub_term_register_input_active() call when the
terminal is (re)activated; the BIOS input had no `.init` before, and a NULL-init terminal is handled by the
`! term->init ||` test in term.h, so adding one changes nothing else. grub_console_term_input has no `.fini`.
Gate interplay (same as EFI): `console` plus any second active input, or grub_term_poll_usb set by the native USB
stack, disables the wait and leaves the old spin (now with PAUSE).

== 6. Observations (not issues) ==

- Runtime no-op for current callers: PAUSE does nothing in GRUB_UTIL/emu builds and in the native tests.
- Test-only robustness: tests/efi_console_wait_test.c passes `NULL` as the message of nearly every grub_test_assert
  (about 50 call sites end in `NULL);`). On a passing assertion that is harmless. On a failing one
  grub_test_assert_helper (grub-core/tests/lib/test.c:173) calls failure_append_vtext -> grub_xvasprintf
  (misc.c:1405) -> parse_printf_arg_fmt, which does `fmt = fmt0; while ((c = *fmt++) != 0)` (misc.c:906-907) on
  the NULL pointer, so the test would crash instead of printing "assert failed". CI still goes red; only the
  diagnostic is lost. The BIOS test passes a message everywhere. Not reported as an issue: no product code is
  involved and no failing input exists today; not compiled here.
- Behaviour trade-offs stated by the author: the BIOS wait does not wake on a keypress (a key typed during the wait
  is only seen on the next poll); physical BIOS firmware is untested; the SeaBIOS/QEMU CPU figures in the commit
  messages were not reproduced here. The source only shows that a 20 ms wait is REQUESTED (edx = 20 * 1000): the
  actual duration is whatever the firmware's INT 15h/AH=86h implementation does (the EFI code comment says firmware
  may round its timer up; for BIOS the author tested only SeaBIOS under QEMU/KVM). I therefore make no claim about
  the resulting input latency.
- UNTESTED / UNVERIFIED BIOS failure modes (reasoned from the code only; no BIOS was available and nothing was run;
  neither is reported as an issue because no concrete failing firmware is known):
  a) A BIOS that returns with CF clear but without really waiting is not detected as a failure:
     grub_console_wait() returns 1 whenever CF is clear, so grub_getkey() `continue`s without the fallback. Each loop
     iteration would then make two grub_bios_interrupt() calls (INT 16h/AH=1 from grub_console_getkey(), plus INT
     15h/AH=86h), each a protected -> real -> protected round trip, instead of one before the MR, so the spin would
     be more expensive than before while still functional. Presetting CF only protects against firmware that leaves
     CF untouched on success, not against one that clears it and returns early.
  b) A firmware call that never returns (for example a BIOS waiting on an RTC periodic interrupt that never fires)
     would freeze input permanently, since grub_getkey() never regains control to poll. input_wait_failed cannot
     help because it is only set after the call returns. The commit message admits that physical BIOSes are untested
     and that "the fallback cannot recover if a firmware call hangs".
- Hygiene (not a functional failure): the MR adds two native test binaries, bios_console_wait_test and
  efi_console_wait_test (built from tests/ per Makefile.util.def), but touches no .gitignore (rtb diff
