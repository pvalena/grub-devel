## Issues Found

### Issue 1: Docs attach `[/PREFIX]` to the interface argument, but the code parses it from ADDRESS

**Location:** `docs/grub.texi`, `@deffn Command net_add_addr`, line ~9419 (commit 2f6a1cb5b)

The synopsis now reads `@var{interface[/PREFIX]} @var{card} @var{address}`. The code reads the prefix from
`args[2]` (ADDRESS), as do the registered usage string (`SHORTNAME CARD ADDRESS[/PREFIX] [HWADDRESS]`), the
example in commit c931ec3cb (`net_add_addr efinet0 efinet0 10.0.0.140/28`) and the docs commit's own message
("appended to the ADDRESS argument"). Nothing parses `args[0]`: a user following the synopsis and typing
`net_add_addr efinet0/28 efinet0 10.0.0.140` gets no error, `grub_net_add_addr()` copies the name verbatim, and
the result is an interface literally named `efinet0/28` with the default class-based /8 route
`efinet0/28:local`, not the requested /28. The sibling `net_add_route` entry already documents this form as
`@var{ip}[/@var{prefix}]`.

**Draft fix** -- put the prefix on the address, as in the code and in `net_add_route`:

```diff
--- a/docs/grub.texi
+++ b/docs/grub.texi
@@ -9419,7 +9419,7 @@
-@deffn Command net_add_addr @var{interface[/PREFIX]} @var{card} @var{address}
+@deffn Command net_add_addr @var{interface} @var{card} @var{address}[/@var{prefix}]
 Configure additional network @var{interface} with @var{address} on a
 network @var{card}. @var{address} can be either IP in dotted decimal notation,
 or symbolic name which is resolved using DNS lookup. If successful, this command
 also adds local link routing entry with name @var{interface}@samp{:local} via
 @var{interface}. The local link routing entry is created with the default
-subnet of @var{address} if @var{/PREFIX} is not specified.
+subnet of @var{address} if @var{prefix} (1 to 31) is not specified.
```

### Issue 2: The `(int)` cast defeats the `cidr > 31` range check on 64-bit targets

**Location:** `grub-core/net/net.c`, `grub_cmd_addaddr()`, lines ~1165 and ~1181-1182 (commit c931ec3cb)

```c
int cidr;
...
cidr = (int)grub_strtol(&p[1], &q, 10);
if ( (q[0] != '\0') || (cidr > 31) || (cidr < 1) )
```

`grub_strtol()` returns `long`, which is 64-bit on x86_64, arm64, riscv64 and ppc64 builds, and it only flags
overflow above `GRUB_LONG_MAX`. The cast to `int` truncates first, so any value congruent mod 2^32 to 1..31
passes the check: `net_add_addr n0 card 10.0.0.140/4294967324` becomes `(int)4294967324 == 28` and is accepted
as /28 instead of failing with "invalid network prefix". Impact is limited to nonsense input being accepted
with a silently different prefix (the narrowed value is always 1..31, so the shift stays defined); 32-bit
targets are not affected.

**Draft fix** -- keep the value as `long` until it is range-checked:

```diff
--- a/grub-core/net/net.c
+++ b/grub-core/net/net.c
@@ -1164,3 +1164,3 @@
   char *p;
-  int cidr;
+  long cidr;
   const char * q;
@@ -1180,3 +1180,3 @@
     {
-      cidr = (int)grub_strtol(&p[1], &q, 10);
+      cidr = grub_strtol (&p[1], &q, 10);
       if ( (q[0] != '\0') || (cidr > 31) || (cidr < 1) )
```

`grub_net_add_ipv4_local (inf, cidr)` takes `int`; by then `cidr` is only -1 or 1..31, so the implicit
conversion is value-preserving.

## Additional findings

The prior /0 shift UB is fixed: `grub_net_add_ipv4_local()` now only receives -1 (auto 8/16/24) or 1..31, and an
empty `10.0.0.1/` is rejected too (`grub_strtol` returns 0 with no digits). Dropping `! q` is safe, since
`grub_strtoull()` sets `*end` on every path. The prefix only takes effect for IPv4: for an IPv6 address `/1`-`/31`
is silently ignored (`grub_net_add_ipv4_local()` returns early) and `/32`+ is rejected. Commits 3-4 fix commit 1
and could be squashed (commit 1 alone still has the /0 path).
